## 어노테이션

어노테이션은 문법이 `@` 하나로 끝나지만, 정작 중요한 건 **어노테이션 자체는 아무 일도 하지 않는다**는 점이다.
붙이는 건 표시일 뿐이고, 실제 동작은 그 표시를 **읽는 쪽**(컴파일러, 어노테이션 프로세서, 프레임워크의 리플렉션 코드)이 만든다.
여기서는 문법과 함께 **누가 언제 읽는지**를 중심으로 정리한다.

### 어노테이션이란
+ 클래스, 메서드, 필드 등에 부가 정보를 제공하는 **메타데이터**
+ 실행 시 특정 기능을 수행하거나, 컴파일러가 추가적인 처리를 수행할 수 있음
+ 주석(`//`, `/* */`)과 다른 점
    - 주석은 컴파일 시점에 버려지고 **사람만** 읽음
    - 어노테이션은 컴파일러와 프로그램이 읽을 수 있는 형태로 **남음**
+ 코드의 동작 자체를 바꾸지는 않음
    - 어노테이션을 붙였다고 메서드가 다르게 실행되지 않음
    - 그 표시를 보고 다르게 동작하는 코드가 **따로** 있을 뿐
+ Java 5에서 도입. 그전에는 같은 정보를 XML 설정 파일이나 이름 규칙(`testXxx`)으로 표현했음
    - 설정이 코드에서 멀리 떨어져 있어 동기화가 깨지기 쉬웠고, 오타는 런타임에야 드러났음
    - 어노테이션은 **대상 바로 위에 붙고** 컴파일러가 위치와 타입을 검사해 줌

### 어노테이션을 읽는 세 시점
+ 어떤 어노테이션이든 아래 셋 중 하나가 읽어야 의미가 생김

    | 읽는 주체 | 시점 | 예 |
    |------|------|-----|
    | 컴파일러 | 컴파일 중, 검사만 하고 버림 | `@Override`, `@SuppressWarnings`, `@FunctionalInterface` |
    | 어노테이션 프로세서 | 컴파일 중, 코드를 생성 | Lombok, MapStruct, Dagger |
    | 리플렉션 | 실행 중 | Spring, JPA, JUnit, Jackson |

+ 어느 시점까지 살아남는지는 `@Retention`이 정함 — 아래 [@Retention](#retention--언제까지-살아남는가)에서 다룸
+ **읽는 쪽을 정하지 않고 만든 어노테이션은 주석과 같음**

### @Override
+ 부모 메서드를 재정의(오버라이딩)할 것임을 명시

    ```java
    class Parent {
        void show() { System.out.println("Parent"); }
    }

    class Child extends Parent {
        @Override // 부모 메서드를 재정의(오버라이딩)할 것임을 명시
        void show() { System.out.println("Child"); }
    }
    ```

+ 컴파일러가 **실제로 재정의가 맞는지 검사** — 아니면 컴파일 에러
+ 붙이지 않으면 못 잡는 대표적 실수

    ```java
    class Person {
        public boolean equals(Person other) { ... }   // ❌ 오버라이딩이 아니라 오버로딩
    }
    ```

    - `Object.equals(Object)`를 재정의한 게 아니라 **새 메서드를 하나 더 만든 것**
    - 컬렉션은 `equals(Object)`를 호출하므로 이 메서드는 영원히 안 불림
    - `@Override`를 붙였다면 컴파일 에러로 즉시 드러남
+ Java 6부터 **인터페이스 구현 메서드에도** 붙일 수 있음
+ 동작을 바꾸지 않음. **공짜로 얻는 컴파일 타임 검사**
+ `@Retention`이 `SOURCE`라 클래스 파일에는 남지 않음

### @Deprecated
+ 해당 요소가 더 이상 사용이 권장되지 않음을 나타냄

    ```java
    @Deprecated // 의미 부여: 해당 메서드는 사용이 권장되지 않음을 나타냄
    void oldMethod() {
        System.out.println("더 이상 사용되지 않는 메서드");
    }
    ```

+ 쓰는 쪽에 컴파일 경고가 뜨고 IDE에서는 취소선이 그어짐
+ **대체재를 반드시 적어야 함** — 이건 어노테이션이 아니라 javadoc 태그의 몫

    ```java
    /**
     * @deprecated 대신 {@link #newMethod()} 를 사용하세요.
     */
    @Deprecated(since = "2.1", forRemoval = true)
    void oldMethod() { ... }
    ```

    - `@Deprecated`(대문자) — 컴파일러용 표시
    - `@deprecated`(소문자) — 문서용 설명
+ Java 9부터 속성이 추가됨
    - `since` — 언제부터 폐기됐는지
    - `forRemoval = true` — **삭제 예정**이라는 뜻으로, 더 강한 경고가 나감
+ `@Retention`이 `RUNTIME`

### @SuppressWarnings
+ 특정 컴파일 경고를 숨김

    ```java
    @SuppressWarnings("unchecked")
    List<String> list = (List<String>) rawList;   // 안전한 캐스팅임을 확인했음
    ```

+ 자주 쓰는 값 — `unchecked`, `rawtypes`, `deprecation`, `serial`, `unused`, `all`
+ **범위를 최소로** — 클래스가 아니라 그 변수·그 메서드 하나에만 붙임
    - 클래스에 붙이면 나중에 생긴 진짜 경고까지 같이 묻힘
+ 왜 억눌러도 되는지 주석으로 남기는 게 좋음 — 경고를 없앤 게 아니라 **판단했다는 기록**

### @FunctionalInterface (Java 8+)
+ 추상 메서드가 정확히 하나인지 컴파일러가 검사

    ```java
    @FunctionalInterface
    interface Calculator {
        int apply(int a, int b);                          // 추상 메서드 하나

        default int twice(int a) { return apply(a, a); }  // default는 개수에 안 들어감
        static Calculator plus() { return Integer::sum; } // static도 마찬가지
    }
    ```

+ 추상 메서드가 둘이 되는 순간 **선언부에서** 컴파일 에러
    - 안 붙였다면 그 인터페이스를 람다로 쓰던 **모든 호출부**가 깨짐
+ 안 붙여도 추상 메서드가 하나면 람다로 쓸 수 있음 — **의도를 고정하는 표시**

### @SafeVarargs
+ 제네릭 가변인자에서 나오는 힙 오염(heap pollution) 경고를 억제

    ```java
    @SafeVarargs
    static <T> List<T> listOf(T... items) { return Arrays.asList(items); }
    ```

+ `static`, `final`, `private` 메서드와 생성자에만 붙일 수 있음
    - 오버라이드 가능한 메서드라면 자식이 안전하지 않게 구현할 수 있어 보장이 깨짐

### 메타 어노테이션
+ **어노테이션에 붙이는 어노테이션.** `java.lang.annotation` 패키지에 있음

    | 어노테이션 | 정하는 것 |
    |------|------|
    | `@Retention` | 어느 시점까지 살아남는가 |
    | `@Target` | 어디에 붙일 수 있는가 |
    | `@Documented` | javadoc에 표시할 것인가 |
    | `@Inherited` | 자식 클래스가 물려받는가 |
    | `@Repeatable` | 같은 자리에 여러 번 붙일 수 있는가 |

### @Retention — 언제까지 살아남는가
```java
@Retention(RetentionPolicy.RUNTIME) // 실행 시간까지 유지
```

| 정책 | 유지 범위 | 읽는 주체 | 예 |
|------|------|------|-----|
| `SOURCE` | 컴파일하면 사라짐 | 컴파일러, 어노테이션 프로세서 | `@Override`, `@SuppressWarnings`, Lombok |
| `CLASS` | `.class`엔 남지만 JVM에 안 올라감 (**기본값**) | 바이트코드 조작·정적 분석 도구 | 일부 분석 도구 |
| `RUNTIME` | 실행 중 리플렉션으로 읽을 수 있음 | 프레임워크 | `@Autowired`, `@Test`, `@Entity` |

+ ⚠️ **기본값이 `CLASS`** — 명시하지 않으면 리플렉션으로 못 읽음
    - 커스텀 어노테이션을 만들었는데 `getAnnotation()`이 계속 `null`을 반환하는 사고의 대부분이 이것
+ `RUNTIME`은 클래스 메타데이터가 계속 메모리에 남으므로, **런타임에 읽을 것만** 지정

### @Target — 어디에 붙일 수 있는가
```java
@Target(ElementType.METHOD)                          // 메서드에서 사용 가능
@Target({ElementType.METHOD, ElementType.FIELD})     // 여러 곳
```

| ElementType | 붙는 자리 |
|------|------|
| `TYPE` | 클래스, 인터페이스, enum, 어노테이션 |
| `FIELD` | 필드, enum 상수 |
| `METHOD` | 메서드 |
| `PARAMETER` | 메서드 파라미터 |
| `CONSTRUCTOR` | 생성자 |
| `LOCAL_VARIABLE` | 지역 변수 |
| `ANNOTATION_TYPE` | 어노테이션 (메타 어노테이션용) |
| `PACKAGE` | 패키지 (`package-info.java`) |
| `TYPE_PARAMETER` | 제네릭 타입 변수 `<T>` (Java 8+) |
| `TYPE_USE` | 타입이 쓰이는 모든 자리 (Java 8+) |
| `MODULE` | 모듈 (Java 9+) |
| `RECORD_COMPONENT` | 레코드 컴포넌트 (Java 16+) |

+ 생략하면 `TYPE_PARAMETER`·`TYPE_USE`를 제외한 대부분의 자리에 붙일 수 있게 됨
+ 좁혀두면 **엉뚱한 데 붙었을 때 컴파일 에러**로 잡힘 — 붙는 자리가 정해져 있다면 반드시 지정

### @Documented와 @Inherited
+ `@Documented` — javadoc에 그 어노테이션이 표시됨. 없으면 문서에서 보이지 않음
+ `@Inherited` — 클래스에 붙은 어노테이션을 자식 클래스가 물려받음

    ```java
    @Inherited
    @Retention(RetentionPolicy.RUNTIME)
    @interface Audited {}

    @Audited class Base {}
    class Sub extends Base {}

    Sub.class.getAnnotation(Audited.class);           // ✅ 있음 (상속됨)
    Sub.class.getDeclaredAnnotation(Audited.class);   // ❌ null (직접 붙은 것만)
    ```

+ ⚠️ `@Inherited`의 함정 세 가지
    - **클래스 상속에만 적용됨** — 인터페이스에 붙은 건 구현체가 물려받지 않음
    - **메서드·필드에는 적용되지 않음** — 오버라이드하면 부모 메서드의 어노테이션은 안 따라옴
    - `getAnnotations()`는 상속을 반영하지만 `getDeclaredAnnotations()`는 아님

### @Repeatable (Java 8+)
+ 같은 어노테이션을 한 자리에 여러 번 붙일 수 있게 함

    ```java
    @Repeatable(Schedules.class)          // 담아둘 컨테이너를 지정
    @Retention(RetentionPolicy.RUNTIME)
    @interface Schedule { String day(); }

    @Retention(RetentionPolicy.RUNTIME)
    @interface Schedules { Schedule[] value(); }   // 컨테이너는 배열 속성 value 필요

    @Schedule(day = "MON")
    @Schedule(day = "FRI")
    void job() {}
    ```

+ 컴파일러가 내부적으로 `@Schedules({...})` 하나로 묶음
+ 읽을 때는 `getAnnotation()`이 아니라 **`getAnnotationsByType(Schedule.class)`**
+ Java 8 이전에는 배열 속성으로 직접 표현했음 — `@Schedules({@Schedule(...), @Schedule(...)})`

### 커스텀 어노테이션 만들기
```java
import java.lang.annotation.*;

@Retention(RetentionPolicy.RUNTIME) // 실행 시간까지 유지
@Target(ElementType.METHOD) // 메서드에서 사용 가능
@interface MyAnnotation {
    String value(); // 속성 추가 가능
}

class Test {
    // 직접 만든 Annotation 사용
    @MyAnnotation(value = "Hello")
    void myMethod() {}
}
```

+ `interface`가 아니라 **`@interface`**로 선언
+ 속성은 필드가 아니라 **메서드 형태**로 선언 — 괄호가 붙고, 메서드 이름이 곧 속성 이름
+ `default`로 기본값을 주면 사용할 때 생략 가능

    ```java
    @interface Retry {
        int count() default 3;
        long delayMs() default 1000L;
        String reason();                 // 기본값이 없으면 필수
    }

    @Retry(reason = "네트워크 불안정")     // count, delayMs는 기본값 사용
    void call() {}
    ```

+ `value` 특례 — 지정할 속성이 `value` 하나뿐이면 이름을 생략할 수 있음

    ```java
    @MyAnnotation("Hello")        // == @MyAnnotation(value = "Hello")
    ```

+ 배열 속성은 원소가 하나면 중괄호를 생략할 수 있음

    ```java
    @interface Roles { String[] value(); }

    @Roles({"ADMIN", "USER"})
    @Roles("ADMIN")               // == @Roles({"ADMIN"})
    ```

+ 속성이 하나도 없으면 **마커 어노테이션** — 괄호 없이 `@MyMarker`로 씀
    - `Serializable` 같은 마커 인터페이스와 역할이 비슷하지만, 어노테이션은 **타입이 되지 않음**
    - 즉 마커 어노테이션으로는 `instanceof` 검사나 타입 제한을 걸 수 없음

### 속성에 쓸 수 있는 타입
+ 아래 타입과 **그 1차원 배열만** 가능

    | 쓸 수 있는 것 | 예 |
    |------|------|
    | 기본형 8가지 | `int count()` |
    | `String` | `String reason()` |
    | `Class` | `Class<?> handler()` |
    | enum | `Level level() default Level.INFO` |
    | 다른 어노테이션 | `Retry retry()` |
    | 위 타입의 1차원 배열 | `String[] roles()` |

+ `List`, 임의의 객체, 2차원 배열은 **컴파일 에러**
+ ⚠️ **`null`을 기본값으로 둘 수 없음**
    - "값 없음"을 표현하려면 빈 문자열, 빈 배열, `Void.class` 같은 **특수 값을 약속**해야 함
+ 값은 **컴파일 타임 상수**여야 함

    ```java
    static final int N = 3;
    @Retry(count = N)             // ✅ 컴파일 타임 상수
    @Retry(count = compute())     // ❌ 컴파일 에러 — 메서드 호출 불가
    ```

+ 그래서 어노테이션에는 **정적인 설정만** 담을 수 있고, 동적인 값은 그걸 읽는 코드가 계산해야 함

### 어노테이션은 그 자체로 아무 일도 하지 않는다
+ 가장 중요한 성질. `@MyAnnotation`을 붙인 것만으로는 **아무 일도 일어나지 않음**
+ 반드시 읽는 쪽이 있어야 함 — 컴파일러 / 어노테이션 프로세서 / 리플렉션
+ `@Transactional`이 트랜잭션을 여는 것도, Spring이 그 표시를 보고 **프록시를 만들어 주기 때문**
    - 스프링 컨텍스트 밖에서 그냥 `new`로 만든 객체에 붙어 있으면 아무 효과가 없음
+ 커스텀 어노테이션을 설계할 때는 **"누가 언제 읽는가"를 먼저 정하고** `@Retention`을 거기에 맞춤

### 리플렉션으로 읽기 (런타임)
```java
import java.lang.reflect.Method;

Method m = Test.class.getDeclaredMethod("myMethod");

if (m.isAnnotationPresent(MyAnnotation.class)) {          // 붙어 있는지
    MyAnnotation a = m.getAnnotation(MyAnnotation.class);
    System.out.println(a.value());                        // "Hello"
}
```

+ 주요 API — `Class`, `Method`, `Field`, `Constructor`, `Parameter`가 모두 `AnnotatedElement`를 구현하므로 사용법이 동일

    | 메서드 | 하는 일 |
    |------|------|
    | `isAnnotationPresent(X.class)` | 붙어 있는지 여부 |
    | `getAnnotation(X.class)` | 어노테이션 인스턴스, 없으면 `null` |
    | `getAnnotations()` | 붙은 것 전부 (`@Inherited`로 상속된 것 포함) |
    | `getDeclaredAnnotations()` | **직접** 붙은 것만 |
    | `getAnnotationsByType(X.class)` | `@Repeatable`까지 포함해 배열로 |

+ 아주 작은 테스트 러너 — JUnit이 하는 일의 뼈대

    ```java
    Object instance = target.getDeclaredConstructor().newInstance();

    for (Method m : target.getDeclaredMethods()) {
        if (m.isAnnotationPresent(MyTest.class)) {
            m.setAccessible(true);
            m.invoke(instance);                            // 표시된 메서드만 실행
        }
    }
    ```

    - 어노테이션이 하는 일은 **"이 메서드를 골라라"는 표시**가 전부
    - 실행 로직은 전부 읽는 쪽 코드에 있음
+ ⚠️ `@Retention(RUNTIME)`이 아니면 여기서 **아무것도 보이지 않음**
+ ⚠️ 리플렉션 호출은 예외를 감싸서 던짐 — `m.invoke()` 안에서 난 예외는 `InvocationTargetException`에 포장되므로 `getCause()`로 꺼내야 원래 예외가 보임

### 컴파일 타임에 읽기 — 어노테이션 프로세서
+ `javax.annotation.processing.Processor` 구현체를 컴파일 과정에 끼워 넣는 방식
+ 컴파일러가 소스를 파싱한 결과를 넘겨주고, 프로세서는 **새 소스 파일을 생성**함
    - 기존 코드를 고치는 게 아니라 **추가**하는 것이 원칙
+ 대표적인 예
    - **Lombok** — `@Getter`, `@Builder`. 표준 범위를 넘어 AST를 직접 조작해서 논란이 있는 방식
    - **MapStruct** — 매퍼 인터페이스를 보고 구현 클래스를 생성
    - **Dagger** — 의존성 주입 코드를 생성
+ 런타임 리플렉션과 비교

    | | 어노테이션 프로세서 | 런타임 리플렉션 |
    |---|---|---|
    | 시점 | 컴파일 | 실행 중 |
    | 비용 | 빌드 시간에 한 번 | 실행할 때마다 |
    | 오류 발견 | 컴파일 에러 | 런타임 예외 |
    | 디버깅 | 생성된 소스를 직접 볼 수 있음 | 스택 트레이스가 깊고 읽기 어려움 |
    | 필요한 Retention | `SOURCE`면 충분 | `RUNTIME` 필수 |

+ 정리 — **컴파일 타임에 끝낼 수 있으면 그쪽이 항상 유리**

### 타입 어노테이션 (Java 8+)
+ `ElementType.TYPE_USE` — **타입이 쓰이는 모든 자리**에 붙일 수 있음

    ```java
    @NonNull String name;                       // 필드 타입
    List<@NonNull String> names;                // 제네릭 인자
    String s = (@NonNull String) obj;           // 캐스팅
    void read() throws @Critical IOException {} // throws 절
    ```

+ 자바 컴파일러는 이 어노테이션들을 **검사하지 않음** — Checker Framework 같은 외부 정적 분석 도구가 읽음
+ 실무에서 흔한 `@Nullable`/`@NonNull`이 이 부류
    - ⚠️ 표준이 아니라 JSR-305, JetBrains, Jakarta 등 **여러 라이브러리에 같은 이름이 흩어져 있음**
    - 프로젝트 안에서 **하나로 통일**해서 쓰지 않으면 도구가 인식하지 못함

### 어노테이션과 상속
+ 자바가 보장하는 범위는 생각보다 훨씬 좁음

    | 상황 | 물려받는가 |
    |------|:--:|
    | 클래스에 붙음 + `@Inherited` → 자식 클래스 | ✅ |
    | 클래스에 붙음, `@Inherited` 없음 → 자식 클래스 | ❌ |
    | 인터페이스에 붙음 → 구현 클래스 | ❌ (`@Inherited`가 있어도) |
    | 메서드에 붙음 → 오버라이드한 메서드 | ❌ |

+ 그래서 부모 메서드의 `@Transactional`이 오버라이드한 메서드에서 사라진 것처럼 보이는 사고가 생김
+ 프레임워크들은 이 한계를 **자체 탐색 로직으로 메움**
    - Spring의 `AnnotatedElementUtils`는 인터페이스와 부모 메서드까지 직접 뒤짐
+ 즉 "어노테이션이 상속되는가"는 **프레임워크마다 다르게 구현한 동작**이지 자바가 보장하는 규칙이 아님

### 실무에서 마주치는 어노테이션
| 영역 | 대표 어노테이션 | 읽는 시점 |
|------|------|------|
| Spring | `@Component`, `@Autowired`, `@Transactional`, `@RequestMapping` | 런타임 리플렉션 |
| JPA | `@Entity`, `@Id`, `@Column`, `@OneToMany` | 런타임 리플렉션 |
| JUnit 5 | `@Test`, `@BeforeEach`, `@ParameterizedTest` | 런타임 리플렉션 |
| Bean Validation | `@NotNull`, `@Size`, `@Email` | 런타임 리플렉션 |
| Jackson | `@JsonProperty`, `@JsonIgnore` | 런타임 리플렉션 |
| Lombok | `@Getter`, `@Builder`, `@Slf4j` | 컴파일 타임 생성 |

+ 대부분이 `RUNTIME` + 리플렉션 조합
    - 그래서 **설정이 틀려도 컴파일은 통과하고 실행할 때 터짐**
    - 반대로 Lombok 계열은 컴파일 시점에 결과가 확정되어 클래스 파일에 실제 메서드가 들어 있음

### 어노테이션 기반 설정의 비용
+ 장점
    - 설정이 대상 **바로 옆**에 있어 읽기 쉽고, 코드와 설정이 함께 움직임
    - 컴파일러가 붙는 자리와 속성 타입을 검사해 줌
+ 단점
    - **설정이 코드에 박힘** — 환경마다 달라야 하는 값은 결국 외부 설정으로 빼야 함
    - 라이브러리 어노테이션을 붙이는 순간 **도메인 클래스가 그 라이브러리에 의존**함
        + 엔티티에 Jackson 어노테이션이 붙기 시작하면 도메인이 표현 계층을 알게 됨
    - **동작이 코드에 보이지 않음** — `@Transactional` 한 줄 뒤에 프록시가 숨어 있음
    - 리플렉션 조회 비용이 실재함 — 프레임워크들이 결과를 캐싱하는 이유
        + 요청마다 리플렉션을 도는 코드를 직접 짜면 그 비용을 그대로 냄
+ 그래서 **프레임워크 경계에는 어노테이션, 내 도메인 코드에는 명시적 호출**이 유지보수에 유리

### 실무 기준
+ 재정의할 때는 `@Override`를 **항상** 붙인다 — 공짜로 컴파일 타임 검사를 얻는다
+ 커스텀 어노테이션에는 `@Retention`과 `@Target`을 **반드시 명시**한다 — 기본값(`CLASS`, 거의 모든 자리)은 대개 원하는 게 아니다
+ 만들기 전에 **읽는 쪽을 먼저 정한다** — 읽는 코드가 없으면 아무 일도 일어나지 않는다
+ `@SuppressWarnings`는 **가장 좁은 범위**에 붙이고 이유를 주석으로 남긴다
+ `@Deprecated`에는 **대체재를 javadoc으로 함께 적는다**
+ 컴파일 타임에 검증할 수 있으면 런타임 리플렉션보다 그쪽을 고른다
+ 어노테이션에 로직을 담으려 하지 않는다 — 담을 수 있는 건 컴파일 타임 상수뿐이다

### 자주 하는 착각
+ "어노테이션을 붙이면 기능이 동작한다"
    - 표시일 뿐. 읽는 코드가 없으면 주석과 다를 게 없음
+ "어노테이션은 주석의 일종이다"
    - 주석은 컴파일 후 사라져 사람만 읽음. 어노테이션은 클래스 파일에 남아 **프로그램이 읽음**
+ "`@Retention`은 생략해도 된다"
    - 기본값이 `CLASS`라 리플렉션으로 읽히지 않음. 프레임워크용이면 `RUNTIME` 필수
+ "`@Override`는 없어도 되는 장식이다"
    - 시그니처 실수를 컴파일 타임에 잡아주는 **유일한 수단**
+ "어노테이션 속성에는 아무 값이나 넣을 수 있다"
    - 기본형·`String`·`Class`·enum·어노테이션과 그 1차원 배열뿐. `null`도 못 넣음
+ "속성 값에 메서드 호출 결과를 쓸 수 있다"
    - 컴파일 타임 상수만 가능. 동적인 값은 읽는 쪽에서 계산해야 함
+ "부모 클래스의 어노테이션은 자식이 물려받는다"
    - `@Inherited`가 있어야 하고, 그마저도 **클래스 상속에만** 적용됨
+ "인터페이스에 `@Inherited`를 붙이면 구현체가 물려받는다"
    - 인터페이스에는 적용되지 않음
+ "메서드를 오버라이드하면 어노테이션도 따라온다"
    - 따라오지 않음. Spring 같은 프레임워크가 **따로 찾아주는 것**뿐
+ "어노테이션은 성능에 영향이 없다"
    - `SOURCE`·`CLASS`는 그렇지만, 런타임에 리플렉션으로 읽는 비용은 실재함
+ "Lombok은 런타임에 getter를 만들어 준다"
    - **컴파일 시점**에 코드를 생성함. 클래스 파일에는 실제 메서드가 들어 있음
+ "`@FunctionalInterface`가 있어야 람다로 쓸 수 있다"
    - 없어도 추상 메서드가 하나면 됨. 그 조건이 깨지는 걸 막아주는 표시
+ "`@Deprecated`를 붙이면 컴파일 에러가 난다"
    - 경고일 뿐. `forRemoval = true`여도 컴파일은 통과함
+ "마커 어노테이션은 마커 인터페이스와 같다"
    - 어노테이션은 **타입이 아니라서** `instanceof` 검사나 타입 제한에는 쓸 수 없음
