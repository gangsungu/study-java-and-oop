## 예외 처리 방법

예외 처리 문법은 `try-catch`, `throws`, `throw` 셋으로 끝나 보이지만, 실제로 헷갈리는 건 **어떤 순서로 실행되고 무엇이 생략되는가**다.
`finally`가 예외를 조용히 삼키거나 `close()`가 진짜 원인을 덮어버리는 문제는 전부 이 실행 순서에서 나온다.
여기서는 문법과 실행 순서를 정리하고, **어디서 잡을지·어떻게 설계할지**는 [예외 처리 전략](예외-처리-전략.md)에서 다룬다.

### 예외 처리 방법과 throw 사용
+ 자바에서 예외를 처리하는 방법은 try-catch, throws, throw 세 가지가 있음
    - try-catch: 예외 발생 시 특정 코드를 실행하여 프로그램이 정상적으로 동작하도록 처리
        ```java
        try {
            int result = 10 / 0; // 예외 발생 (ArithmeticException)
        } catch (ArithmeticException e) {
            System.out.println("예외 발생: " + e.getMessage());
        }
        ```
    - throws: 메서드에서 예외가 발생할 가능성이 있음을 호출하는 쪽에 알림
        ```java
        // 여기서 처리하지 않고 호출한 쪽으로 넘김 — 해결이 아니라 책임을 미루는 것
        String read(String path) throws IOException {
            return Files.readString(Path.of(path));   // IOException을 던질 수 있음
        }
        ```
    - throw: 직접 예외를 발생시킬 때 사용
        ```java
        void checkAge(int age) throws IllegalArgumentException {
            if (age < 0) {
                throw new IllegalArgumentException("나이는 음수가 될 수 없습니다");
            }
            System.out.println("입력한 나이: " + age);
        }
        ```
+ `throw`와 `throws`는 이름만 비슷하고 하는 일이 반대임

    | | `throw` | `throws` |
    |---|---|---|
    | 위치 | 메서드 **본문 안** | 메서드 **선언부** |
    | 하는 일 | 예외를 **지금 발생시킴** | 이 메서드가 예외를 던질 수 있다고 **알림** |
    | 대상 | 인스턴스 (`new ...`) | 타입 |
    | 개수 | 한 번에 하나 | 쉼표로 여러 개 |

+ unchecked 예외에 `throws`를 붙이는 것은 문법상 되지만 강제력이 없음
    - 위 `checkAge`의 `throws IllegalArgumentException`이 그 경우 — 호출하는 쪽이 아무것도 안 해도 컴파일됨
    - 문서 역할만 하므로 보통은 Javadoc `@throws`로 남김

### try-catch-finally의 실행 순서
+ `finally`는 예외가 나든 안 나든, 중간에 `return`을 하든 **항상 실행됨**
    - 자원 반납·락 해제처럼 반드시 해야 하는 뒷정리를 두는 자리

    ```java
    try {
        return "정상";
    } catch (Exception e) {
        return "예외";
    } finally {
        System.out.println("항상 실행");   // 반환값이 확정된 뒤, 실제로 반환되기 직전에 실행됨
    }
    ```

+ 경우별 실행 순서
    - 예외 없음 → `try` → `finally`
    - 예외 발생 + 잡는 `catch` 있음 → `try`(예외 지점까지) → `catch` → `finally`
    - 예외 발생 + 잡는 `catch` 없음 → `try`(예외 지점까지) → `finally` → 호출한 쪽으로 예외 전파
+ `finally`가 실행되지 않는 경우
    - `System.exit()` 호출
    - JVM이 죽거나 스레드가 강제로 종료됨
    - `try` 블록 안에서 무한 루프·데드락에 빠져 블록을 빠져나오지 못함
+ ❌ `finally`에서 `return`하거나 예외를 던지면 **원래 예외가 사라짐**

    ```java
    static int bad() {
        try {
            throw new IllegalStateException("진짜 원인");
        } finally {
            return 0;   // ❌ 예외가 삼켜지고 조용히 0이 반환됨
        }
    }
    ```

    - 컴파일러도 `finally block does not complete normally` 경고를 냄
    - `finally`에는 **값을 반환하지도, 예외를 던지지도 않는 코드만** 둘 것

### catch 블록이 여러 개일 때
+ 위에서부터 검사해서 **처음 매칭되는 catch 하나만** 실행됨
+ 하위 예외를 먼저, 상위 예외를 나중에 써야 함

    ```java
    try {
        ...
    } catch (FileNotFoundException e) {   // 하위 먼저
        ...
    } catch (IOException e) {             // 상위 나중
        ...
    }
    ```

    - 순서를 바꾸면 아래쪽이 영원히 도달할 수 없으므로 **컴파일 에러** (`has already been caught`)
+ multi-catch (Java 7+) — 처리 방식이 같으면 `|`로 묶음

    ```java
    try {
        ...
    } catch (IOException | SQLException e) {
        log.error("외부 자원 접근 실패", e);
    }
    ```

    - 묶는 타입끼리 **상속 관계면 안 됨** (`IOException | FileNotFoundException`은 컴파일 에러)
    - 이때 `e`는 **암묵적으로 final**이라 재대입할 수 없음
    - `e`의 정적 타입은 묶은 타입들의 **공통 상위 타입**이 됨

### try-with-resources (Java 7+)
+ `AutoCloseable`을 구현한 자원을 **블록이 끝날 때 자동으로 닫아줌**

    ```java
    try (BufferedReader br = new BufferedReader(new FileReader("a.txt"))) {
        return br.readLine();
    }   // br.close()가 자동 호출됨 — catch나 finally가 없어도 닫힘
    ```

+ `finally`로 직접 닫으면 생기는 문제

    ```java
    BufferedReader br = null;
    try {
        br = new BufferedReader(new FileReader("a.txt"));
        return br.readLine();          // ① 여기서 IOException 발생
    } finally {
        if (br != null) br.close();    // ② close()에서도 예외가 나면
    }                                  // → ②가 ①을 덮어써서 진짜 원인이 사라짐
    ```

    - try-with-resources는 ①을 주 예외로 두고 ②를 **suppressed(억제된) 예외**로 붙여 둘 다 남김
    - `e.getSuppressed()`로 꺼내볼 수 있고, 스택 트레이스에도 `Suppressed:`로 찍힘
+ 세부 규칙
    - 자원이 여러 개면 `;`로 나열하고, **선언의 역순으로** 닫힘
    - 자원 변수는 암묵적으로 `final`
    - `close()`가 `catch`/`finally`보다 **먼저** 실행됨 (닫고 나서 잡음)
    - Java 9+에서는 이미 선언된 effectively final 변수를 괄호 안에 그대로 쓸 수 있음

        ```java
        BufferedReader br = new BufferedReader(new FileReader("a.txt"));
        try (br) { ... }   // Java 9+
        ```

### 자바 예외 계층 구조
+ 자바 예외 계층 구조
    - 모든 예외의 최상위 부모는 Throwable 클래스임
    - Throwable은 두 종류로 나뉨: Error와 Exception
    - Error는 복구 불가능한 시스템 레벨 문제를 의미함
    - Exception은 프로그램 흐름에서 발생 가능한 문제 상황을 의미함
+ Error
    - 메모리 부족, 스택 오버플로우 같은 치명적인 문제를 의미
    - 개발자가 처리할 수 없기 때문에 예외 처리 대상이 아님
+ Exception
    - 개발자가 적절히 처리해야 하는 문제가 발생했음을 의미
    - 대표적으로 IOException, SQLException 등 외부 자원 사용 시 발생하는 예외가 포함

    ```
    Throwable
    ├── Error                              ← 복구 불가, 잡지 않음 (unchecked)
    │     ├── OutOfMemoryError
    │     └── StackOverflowError
    └── Exception                          ← 여기서부터 checked
            ├── IOException
            │     └── FileNotFoundException
            ├── SQLException
            └── RuntimeException           ← 이 가지만 unchecked
                    ├── NullPointerException
                    ├── IllegalArgumentException
                    ├── IllegalStateException
                    ├── IndexOutOfBoundsException
                    └── ... (다수의 하위 예외)
    ```

+ Throwable의 주요 메서드

    | 메서드 | 하는 일 |
    |---|---|
    | `getMessage()` | 생성할 때 넘긴 메시지 |
    | `getCause()` | 원인 예외 — 감싸서 던졌을 때 안쪽 예외 |
    | `getStackTrace()` | 호출 스택을 배열로 반환 |
    | `printStackTrace()` | 스택 트레이스를 표준 에러로 출력 — **로깅 대신 쓰면 안 됨** |
    | `getSuppressed()` | try-with-resources에서 억제된 예외들 |

+ Error를 잡으면 안 되는 이유
    - `catch (Throwable t)`로 쓰면 문법상 `OutOfMemoryError`도 잡히지만, **잡아도 할 수 있는 일이 없음**
    - 이미 메모리가 없는 상태라 catch 블록 안에서 로깅조차 실패할 수 있음
    - 그래서 잡는 범위의 상한은 `Exception`으로 둠

### Checked Exception vs Unchecked Exception
+ 나누는 기준은 **컴파일러가 처리를 강제하는가** 하나뿐임
    - `RuntimeException` 계열과 `Error` 계열 → unchecked
    - 그 외 `Exception` 하위 전부 → checked
+ Checked Exception
    - 컴파일 단계에서 반드시 처리해야 하는 예외임
    - try-catch 또는 throws로 처리해야 컴파일 통과함
    - 외부 자원(파일 I/O, 네트워크, DB) 사용 시 주로 발생함
    - 안정성을 위한 강제 처리 메커니즘임
    - 예시
        + IOException
        + SQLException
        + FileNotFoundException
+ Unchecked Exception
    - 컴파일러가 예외 처리를 강제하지 않는 예외임
    - 실행 중(Runtime)에 발생하므로 RuntimeException 계열에 속함
    - 주로 프로그래머의 실수로 인해 발생함
    - 방어적 프로그래밍이 핵심임
    - 예시
        + NullPointerException
        + IndexOutOfBoundsException
        + IllegalArgumentException

    | | Checked | Unchecked |
    |---|---|---|
    | 범위 | `Exception` 하위에서 `RuntimeException` 계열을 뺀 나머지 | `RuntimeException` 계열 + `Error` 계열 |
    | 컴파일러 강제 | O — try-catch나 throws 필수 | X |
    | 발생 원인 | 주로 외부 환경 문제 | 주로 코드의 논리 오류 |
    | 성격 | 호출자가 **복구를 시도해볼 수 있는** 상황 | 프로그래밍 오류이거나 복구 불가 |

+ 오버라이딩할 때는 부모가 선언한 checked 예외보다 **넓게 던질 수 없음**
    - unchecked 예외는 제한이 없음
    - 자세한 규칙은 [자바의 OOP — 오버라이딩](../04-자바와-객체지향-프로그래밍/자바의-OOP.md#오버라이딩) 참고
+ 둘 중 무엇을 쓸지, 실무에서 왜 unchecked로 기우는지는 [예외 처리 전략](예외-처리-전략.md#checked-exception이-실무에서-덜-쓰이는-이유)에서 다룸

### 자주 하는 착각
+ "`finally`는 무조건 실행된다"
    - `System.exit()`이나 JVM 종료 앞에서는 실행되지 않음
+ "`try` 안에서 `return`하면 `finally`를 건너뛴다"
    - 반환값만 확정해두고 `finally`를 실행한 뒤 반환함. 건너뛰지 않음
+ "`finally`에서 `return`해도 된다"
    - 진행 중이던 예외와 `try`의 반환값을 **덮어써서 조용히 없애버림**
+ "catch 블록 순서는 상관없다"
    - 상위 예외를 먼저 쓰면 아래쪽이 도달 불가라서 **컴파일 에러**
+ "multi-catch로 아무 예외나 묶을 수 있다"
    - 상속 관계인 타입끼리는 못 묶음. 어차피 상위 하나로 잡히기 때문
+ "unchecked 예외는 `RuntimeException` 계열뿐이다"
    - `Error` 계열도 unchecked임. 기준은 계층이 아니라 **컴파일러가 강제하는지**
+ "try-with-resources를 쓰면 `finally`가 필요 없다"
    - 자원 닫기만 대신해줌. 락 해제 같은 다른 뒷정리는 여전히 `finally`
+ "`close()`에서 난 예외 때문에 원래 예외를 못 본다"
    - try-with-resources는 원래 예외를 주 예외로 두고 `close()` 예외를 **suppressed로 함께 남김**
+ "`throws`를 선언하면 예외가 처리된 것이다"
    - **책임을 호출자에게 미룬 것**뿐. 아무도 안 잡으면 그대로 종료됨
