## 예외 처리 전략

문법을 다 알아도 예외 처리는 여전히 어렵다. 어려운 쪽이 **어디서 잡을지**이기 때문이다.
실무에서 사고를 내는 코드는 문법이 틀린 코드가 아니라 **잡지 말아야 할 곳에서 잡거나, 잡고 아무것도 하지 않는 코드**다.
문법과 실행 순서는 [예외 처리 방법](예외-처리-방법.md)에 정리했고, 여기서는 그 위에서 하는 선택을 다룬다.

### Checked Exception이 실무에서 덜 쓰이는 이유
+ "복구 가능한 상황을 컴파일러가 챙겨준다"는 의도였지만, 실제로는 세 가지 문제가 생김
+ **throws 전염**
    - 아래쪽 메서드가 checked를 던지면 그걸 호출하는 위쪽 메서드가 전부 `throws`를 달아야 함
    - 결국 귀찮아서 `throws Exception`으로 뭉개거나, 빈 catch로 삼키는 코드가 나옴
+ **람다·스트림과 맞지 않음**

    ```java
    // ❌ 컴파일 에러 — Function.apply()가 checked 예외를 선언하지 않음
    paths.stream().map(p -> Files.readString(p)).toList();
    ```

    - 표준 함수형 인터페이스가 checked 예외를 선언하지 않아서 매번 try-catch로 감싸야 함
+ **호출자가 어차피 복구하지 못함**
    - DB가 죽었을 때 호출한 쪽이 할 수 있는 일은 대개 "로깅하고 실패 응답"뿐
+ 그래서 프레임워크들은 checked를 unchecked로 감싸는 쪽을 택함
    - 스프링이 `SQLException`(checked)을 `DataAccessException`(unchecked)으로 바꿔 던지는 것이 대표적
    - 스프링 `@Transactional`은 기본적으로 **unchecked 예외에서만 롤백**함 (checked는 `rollbackFor` 지정 필요)
+ 그래도 checked가 맞는 자리
    - 호출자가 **실제로 다른 행동을 선택할 수 있을 때** (재시도, 대체 경로, 사용자에게 재입력 요청)
    - 라이브러리 경계에서 "이건 정상 흐름에서도 실패할 수 있다"고 알려야 할 때

### 예외 감싸기와 원인 사슬
+ 계층을 넘길 때는 그 계층의 언어로 바꿔 던지되, **원인을 반드시 같이 넘김**

    ```java
    try {
        return repository.find(id);
    } catch (SQLException e) {
        throw new MemberNotFoundException("회원 조회 실패: id=" + id, e);   // ✅ e를 cause로
    }
    ```

    - 상위 계층이 `SQLException`을 알게 되면 DB 기술이 바뀔 때 같이 바뀜 — 감싸는 이유가 이것
+ ❌ 원인을 빼먹으면 스택 트레이스가 그 지점에서 끊김

    ```java
    throw new MemberNotFoundException("회원 조회 실패");        // ❌ 진짜 원인이 사라짐
    throw new MemberNotFoundException(e.getMessage());        // ❌ 메시지만 복사되고 스택은 끊김
    ```

+ 스택 트레이스 읽는 법

    ```
    MemberNotFoundException: 회원 조회 실패: id=42
        at MemberService.find(MemberService.java:31)
        ... 23 more
    Caused by: SQLException: Connection refused
        at ...
    Caused by: ConnectException: Connection refused      ← 맨 아래가 근본 원인
        at ...
    ```

    - 아래로 갈수록 **원인에 가까움**. 먼저 볼 곳은 맨 아래 `Caused by`
    - `... 23 more`는 위쪽 트레이스와 겹치는 프레임을 생략한 것

### 사용자 정의 예외
+ 언제 만드나
    - 표준 예외로 **의미가 충분히 전달되지 않을 때**만
    - 도메인 규칙 위반(잔액 부족, 중복 가입)처럼 잡는 쪽이 **구분해서 처리해야 하는** 실패
+ 잘 맞는 표준 예외가 있으면 그걸 씀

    | 상황 | 표준 예외 |
    |---|---|
    | 인자 값이 잘못됨 | `IllegalArgumentException` |
    | 지금 상태에서는 할 수 없는 호출 | `IllegalStateException` |
    | 인자가 null이면 안 됨 | `NullPointerException` (`Objects.requireNonNull`) |
    | 아직 구현하지 않음 | `UnsupportedOperationException` |

+ 기본은 `RuntimeException` 상속

    ```java
    public class InsufficientBalanceException extends RuntimeException {
        private final long balance;
        private final long requested;

        public InsufficientBalanceException(long balance, long requested) {
            super("잔액 부족: 보유 " + balance + ", 요청 " + requested);
            this.balance = balance;
            this.requested = requested;
        }

        public long getShortfall() { return requested - balance; }
    }
    ```

    - 메시지 문자열로만 담지 말고 **필요한 값은 필드로** 두면 잡는 쪽에서 꺼내 쓸 수 있음
    - `cause`를 받는 생성자도 같이 열어두면 감싸 던질 때 편함
+ 도메인마다 최상위 예외를 하나 두면 경계에서 잡기 쉬워짐
    - `OrderException`을 두고 그 아래에 구체적인 예외들을 두는 식
    - 전역 핸들러는 최상위 하나만 잡고, 구분이 필요한 곳에서만 하위 타입을 잡음

### 예외 처리 안티패턴
+ ❌ **빈 catch — 예외 삼키기**

    ```java
    try { ... } catch (Exception e) { }   // 아무 일도 없었던 것처럼 진행됨
    ```

    - 무시가 정말 의도라면 **왜 무시해도 되는지 주석**을 남길 것
+ ❌ **`e.printStackTrace()`**
    - 표준 에러로만 나가서 로그 수집에 잡히지 않고, 로그 레벨도 컨텍스트도 없음
    - `log.error("주문 저장 실패, orderId={}", id, e)`처럼 로거에 **예외 객체째로** 넘길 것
+ ❌ **`catch (Exception e)`로 뭉뚱그리기**
    - `NullPointerException` 같은 버그성 예외까지 같이 삼켜서 문제를 숨김
+ ❌ **로깅하고 다시 던지기**

    ```java
    catch (IOException e) {
        log.error("실패", e);
        throw e;              // 위쪽에서 또 로깅하면 같은 예외가 여러 번 찍힘
    }
    ```

    - **로깅은 최종적으로 처리하는 한 곳에서 한 번만**
+ ❌ **예외를 흐름 제어에 쓰기**

    ```java
    try {
        return map.get(key).toString();
    } catch (NullPointerException e) {
        return "없음";        // ❌ 조건문으로 써야 할 자리
    }
    ```

+ ❌ **`throws Exception`으로 선언**
    - 무엇이 실패할 수 있는지 정보가 0이 되고, 호출자도 `catch (Exception)`밖에 못 쓰게 됨
+ ❌ **`InterruptedException` 삼키기**
    - 잡았으면 `Thread.currentThread().interrupt()`로 인터럽트 상태를 복구해야 함

### 예외의 비용
+ 예외 객체 생성 비용의 대부분은 **스택 트레이스를 채우는 것**(`fillInStackTrace()`)
    - 스택이 깊을수록 비쌈. `throw`나 `catch` 자체보다 여기가 압도적임
+ 예외가 발생하지 않으면 `try` 블록은 **사실상 공짜**
    - "성능 때문에 try 범위를 줄인다"는 말에는 근거가 없음
+ 반대로 **루프 안에서 예외가 반복해서 던져지는 코드**는 실측될 만큼 느려짐
    - 예외를 흐름 제어로 쓰면 안 되는 실질적인 이유
+ JIT가 자주 반복되는 예외의 스택 트레이스를 **생략해버리기도 함**
    - 운영 로그에 메시지도 스택도 없는 `NullPointerException`만 찍히는 원인
    - `-XX:-OmitStackTraceInFastThrow`로 끌 수 있음
+ 스택 트레이스가 필요 없는 예외라면 아예 끄는 생성자도 있음
    - `super(message, cause, false, false)` — 마지막 인자가 스택 트레이스 기록 여부
+ Java 14+의 Helpful NullPointerException
    - `a.getB().getC()`에서 **무엇이 null인지** 메시지에 찍어줌 (Java 15부터 기본 활성화)

### 실무 기준
+ **처리할 수 있을 때만 잡는다**
    - 잡아서 할 일이 없으면 그냥 올려보내는 게 맞음
+ **잡는 곳을 경계 한 곳으로 모은다**
    - 웹이라면 `@ControllerAdvice` 같은 전역 핸들러, 배치라면 잡(job) 단위
    - 중간 계층은 감싸서 올리기만 하고 로깅은 하지 않음
+ **예외에 컨텍스트를 담는다**
    - "저장 실패"보다 "주문 저장 실패, orderId=1234"가 로그에서 살아남음
+ **정상 흐름은 예외로 표현하지 않는다**
    - "값이 없음"은 `Optional`이나 빈 컬렉션으로, "규칙 위반"은 예외로

### 자주 하는 착각
+ "예외를 잡으면 처리한 것이다"
    - 로그도 안 남기고 잡으면 처리가 아니라 **문제를 숨긴 것**에 가까움
+ "`catch (Exception e)`가 안전하다"
    - 버그성 예외까지 같이 삼켜서 오히려 위험함
+ "checked 예외가 unchecked보다 안전하다"
    - 강제할 뿐임. 강제당한 코드가 빈 catch가 되면 오히려 더 위험해짐
+ "예외는 낮은 계층에서 바로 잡아야 한다"
    - 거기서는 할 수 있는 일이 없는 경우가 대부분. **판단할 수 있는 곳까지 올리는 것**이 기본
+ "try-catch는 느리다"
    - 예외가 안 나면 비용이 거의 없음. 비싼 건 **예외를 던지는 순간**
+ "커스텀 예외는 많을수록 좋다"
    - 잡는 쪽이 구분해서 처리하지 않을 거면 표준 예외로 충분함
+ "`throw new Exception(e.getMessage())`로 감싸면 원인이 보존된다"
    - 메시지만 복사되고 스택 트레이스는 끊김. **`cause`로 넘겨야** 사슬이 이어짐
+ "예외를 감싸면 원래 예외 정보가 사라진다"
    - `cause`로 넘기면 `Caused by`로 전부 남음. 감싸는 것과 삼키는 것은 다른 일
