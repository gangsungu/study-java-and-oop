## 다형성

다형성이 객체지향 4대 특징 안에서 무엇인지는 [객체 지향이란 — 다형성 자세히 보기](../01-객체지향이란/객체지향이란.md#다형성-자세히-보기) 문서에서 정리했다.
이 문서는 **자바가 다형성을 어떤 규칙과 메커니즘으로 실제로 굴리는지**에 초점을 맞춘다.

### 다형성
+ 같은 인터페이스나 부모 클래스를 공유하는 객체가 서로 다른 동작을 수행할 수 있는 성질
+ 메서드 호출 시, 실행될 구체적인 구현이 실행 시점에 결정됨
+ 성립하려면 세 가지가 **모두** 필요함
    - ① 상속(`extends`) 또는 구현(`implements`) 관계가 있고
    - ② 자식이 메서드를 **오버라이딩**했고
    - ③ **부모(또는 인터페이스) 타입 변수**로 참조할 것
    - 하나라도 빠지면 그냥 평범한 메서드 호출임. 특히 ③이 빠져 자식 타입 변수로 받으면 다형성을 쓸 일 자체가 없음
+ 한 문장으로 정리하면
    - **컴파일러는 선언 타입을 보고 "이 메서드가 있는지"를 검사하고, JVM은 실제 객체를 보고 "어느 구현을 부를지"를 고른다**
    - 이 문서에 나오는 거의 모든 규칙과 함정이 이 한 줄에서 갈린다

+ 메서드 오버라이딩을 사용한 다형성
    - 부모 클래스의 메서드를 자식 클래스에서 재정의하여 다른 동작을 수행

    ```java
    class Animal {
        void makeSound() {
            System.out.println("Some sound");
        }
    }

    class Dog extends Animal {
        @Override
        void makeSound() {
            System.out.println("Bark!");
        }
    }

    Animal myDog = new Dog();
    myDog.makeSound(); // 실행 결과: Bark! (Dog의 메서드 실행)
    ```

+ 인터페이스를 통한 다형성
    - 인터페이스를 구현한 여러 클래스가 같은 메서드를 다르게 구현

    ```java
    interface Shape {
        void draw();
    }

    class Circle implements Shape {
        public void draw() {
            System.out.println("Drawing Circle");
        }
    }

    class Square implements Shape {
        public void draw() {
            System.out.println("Drawing Square");
        }
    }

    Shape s1 = new Circle();
    Shape s2 = new Square();
    s1.draw(); // 출력: Drawing Circle
    s2.draw(); // 출력: Drawing Square
    ```

### 업캐스팅과 다운캐스팅
+ 업캐스팅(Upcasting)
    - 자식 클래스 객체를 부모 클래스 타입으로 참조
    - 메서드 오버라이딩을 통해 다형성을 활용할 때 주로 사용
    - **자동으로 이루어지고 절대 실패하지 않음** — 모든 `Dog`는 반드시 `Animal`이기 때문

    ```java
    class Animal {
        void makeSound() {
            System.out.println("Some sound");
        }
    }

    class Dog extends Animal {
        void bark() {
            System.out.println("Bark!");
        }
    }

    Animal a = new Dog(); // 업캐스팅
    a.makeSound(); // 출력: Some sound(메서드 오버라이딩이 없을 경우)
    a.bark(); // ❌ 컴파일 에러 발생
    ```

    - `a.bark()`가 막히는 이유는 **객체에서 `bark()`가 사라져서가 아님**
        + 힙에 있는 객체는 여전히 완전한 `Dog`이고 `bark()`도 그대로 있음
        + 컴파일러가 선언 타입인 `Animal`만 보고 "`Animal`에 `bark()`가 있나?"를 검사해서 막는 것
        + 그래서 다운캐스팅으로 타입을 되돌리면 다시 보임 — 객체가 복원되는 게 아니라 **시야가 넓어지는 것**

+ 다운캐스팅(Downcasting)
    - 부모 타입을 다시 자식 타입으로 변환 (명시적 형변환 필요)
    - 런타임 오류 발생 가능 (instanceof를 활용하여 안전한 변환 필요)

    ```java
    Animal a = new Dog();
    if (a instanceof Dog) { // 안전하게 다운캐스팅
        Dog d = (Dog) a; // 다운캐스팅
        d.bark(); // 출력: Bark !
    }
    ```

    - 확인 없이 캐스팅하면 **컴파일은 통과하고 런타임에 터짐**

    ```java
    Animal a = new Animal();
    Dog d = (Dog) a;   // 컴파일 OK → 실행 시 ClassCastException
    // 실제 객체가 Animal이므로 Dog로 볼 수 없음. 애초에 Dog였던 적이 없으면 되돌릴 수도 없음
    ```

+ 캐스팅 규칙 정리

    | 상황 | 결과 |
    |------|------|
    | 자식 → 부모 (업캐스팅) | ⭕ 자동, 항상 성공 |
    | 부모 → 자식, 실제 객체가 자식 | ⭕ 명시적 캐스팅으로 성공 |
    | 부모 → 자식, 실제 객체가 부모 | ⚠️ 컴파일 OK / 런타임 `ClassCastException` |
    | 상속 관계가 전혀 없는 타입끼리 | ❌ 컴파일 에러 (`inconvertible types`) |

    - 마지막 줄이 중요함 — `(String) animal`처럼 **가능성이 0인 캐스팅은 컴파일러가 미리 잡아줌**
    - 즉 컴파일러는 "말이 되는 캐스팅인가"까지만 보고, "실제로 그 타입인가"는 런타임에 검사함

+ `instanceof` 주의점
    - **하위 타입이면 전부 `true`** — 정확히 그 타입인지 보는 게 아님

    ```java
    Animal a = new Dog();
    a instanceof Dog;      // true
    a instanceof Animal;   // true  ← 부모 타입에도 true
    a instanceof Object;   // true
    ```

    - 정확히 같은 클래스인지 봐야 한다면 `getClass() == Dog.class`를 씀 (`equals()` 구현에서 자주 갈리는 지점)
    - `null instanceof Dog`는 **`false`** — `NullPointerException`이 아님. 그래서 `instanceof` 하나로 null 검사까지 겸할 수 있음
    - 반대로 `(Dog) null`은 **성공함** (null은 어떤 참조 타입으로든 캐스팅됨)

+ 패턴 매칭 (Java 16+)
    - `instanceof` 검사와 변수 선언을 한 번에 — 검사·캐스팅·대입 세 번 쓰던 것을 한 줄로 줄임

    ```java
    // 기존
    if (a instanceof Dog) {
        Dog d = (Dog) a;
        d.bark();
    }

    // Java 16+
    if (a instanceof Dog d) {   // 검사에 성공하면 d에 바인딩됨
        d.bark();
    }
    ```

    - Java 21부터는 `switch`에서도 쓸 수 있음

    ```java
    switch (a) {
        case Dog d -> d.bark();
        case Cat c -> c.meow();
        default    -> a.makeSound();
    }
    ```

+ 다운캐스팅이 자주 나오면 **설계를 의심할 것**
    - `instanceof`로 타입을 분기하고 있다는 건, 그 분기가 원래 **메서드 오버라이딩으로 풀렸어야 할 일**이라는 신호
    - 아래 [다형성을 쓰는 이유](#다형성을-쓰는-이유) 참고

### 동적 바인딩은 어떻게 동작하나
+ 바인딩(Binding) = "이 호출이 실제로 어느 메서드인지" 연결하는 일
    - **정적 바인딩**: 컴파일 시점에 확정 (선언 타입 기준)
    - **동적 바인딩**: 실행 시점에 확정 (실제 객체 기준) — 다형성이 동작하는 원리

+ JVM이 하는 일 (개념적으로)
    - 클래스마다 **메서드 테이블(가상 메서드 테이블)** 을 하나씩 만들어 메서드 목록을 들고 있음
    - 자식 클래스의 테이블은 부모 것을 복사한 뒤 **오버라이딩한 자리만 자기 구현으로 덮어씀**
    - 힙의 모든 객체는 헤더에 **자기 클래스 정보를 가리키는 포인터**를 들고 있음
    - `a.makeSound()`를 만나면 JVM은 `a`의 선언 타입이 아니라 **`a`가 가리키는 객체의 클래스 테이블**을 타고 들어가 메서드를 찾음
    - 그래서 변수 타입을 아무리 부모로 바꿔도 실행되는 건 항상 실제 객체의 구현임

+ 바이트코드에서는 호출 명령 자체가 나뉘어 있음

    | 명령어 | 대상 | 바인딩 |
    |--------|------|:------:|
    | `invokevirtual` | 일반 인스턴스 메서드 | 동적 |
    | `invokeinterface` | 인터페이스 메서드 | 동적 |
    | `invokestatic` | `static` 메서드 | 정적 |
    | `invokespecial` | 생성자, `private` 메서드, `super.method()` | 정적 |

    - `super.makeSound()`가 부모 구현을 정확히 부르는 것도 이 때문 — `invokespecial`이라 동적 바인딩을 건너뜀
    - `javap -c`로 클래스를 열어보면 오버라이딩 가능한 메서드 호출이 전부 `invokevirtual`로 찍혀 있음

+ 성능 걱정은 대체로 필요 없음
    - 테이블을 한 번 더 타는 비용은 매우 작고, JIT는 실행 중 **실제로 어느 구현이 불리는지 관찰해서** 구현이 하나뿐이거나 소수면 그 자리에 인라인해버림
    - "부모 타입으로 받으면 느리다"는 이유로 다형성을 포기할 이유는 없음

### 다형성이 적용되지 않는 것
+ 동적 바인딩은 **인스턴스 메서드에만** 적용됨. 나머지는 전부 선언 타입 기준

    | 대상 | 기준 | 이유 |
    |------|------|------|
    | 인스턴스 메서드 | **실제 객체** | 유일하게 동적 바인딩됨 |
    | 필드 | 선언 타입 | 오버라이딩이 아니라 **하이딩** |
    | `static` 메서드 | 선언 타입 | 클래스 소속이라 객체와 무관 (**하이딩**) |
    | `private` 메서드 | 선언 타입 | 자식에게 안 보여서 오버라이딩 자체가 성립 안 함 |
    | 오버로딩된 메서드 선택 | 선언 타입 | 어느 오버로딩을 부를지는 **컴파일 시점**에 정해짐 |

    ```java
    class Parent {
        String name = "부모";
        static String who() { return "Parent"; }
        void speak() { System.out.println("부모 말"); }
    }

    class Child extends Parent {
        String name = "자식";
        static String who() { return "Child"; }
        @Override void speak() { System.out.println("자식 말"); }
    }

    Parent p = new Child();
    p.speak();      // 자식 말   ← 실제 객체 기준 (동적 바인딩)
    p.name;         // 부모      ← 선언 타입 기준 (필드 하이딩)
    Parent.who();   // Parent    ← static은 클래스로 호출하는 것이 정상
    ```

    - 필드·`static` 하이딩의 상세한 동작은 [자바의 OOP — this와 super](자바의-OOP.md#this와-super) 참고

+ 생성자 안에서는 다형성이 **위험하게** 동작함
    - 부모 생성자가 도는 시점에도 동적 바인딩은 이미 살아 있어서 **자식의 오버라이딩 메서드가 호출됨**
    - 그런데 자식 필드는 아직 초기화 전이라 `null`/`0`인 상태 → 예시는 [자바의 OOP — 생성자](자바의-OOP.md#생성자) 참고

### 추상 클래스와 인터페이스
+ 자바에서 다형성을 구현하는 대표적인 두 가지 방법
    - 구조는 똑같음 — **부모 타입으로 묶어두고, 실제 동작은 자식이 다르게 구현**
    - 차이는 **무엇을 물려주느냐**에 있음

    | | 물려주는 것 | 관계 |
    |---|---|---|
    | 추상 클래스 | 타입 + **상태(필드)** + **이미 만들어진 구현** | is-a (~의 한 종류다) |
    | 인터페이스 | 타입 + 약속된 메서드 목록 (+ 기본 구현) | can-do (~을 할 수 있다) |

+ 추상 클래스로 구현하는 다형성
    - 공통 필드와 공통 구현은 부모가 갖고, **달라지는 메서드만 `abstract`로 열어둠**

    ```java
    abstract class Animal {
        protected final String name;              // 공통 상태 — 인터페이스는 가질 수 없는 것

        protected Animal(String name) {           // 생성자로 초기화 규칙을 강제
            this.name = name;
        }

        public void sleep() {                     // 공통 구현 — 자식이 그대로 물려받음
            System.out.println(name + ": 쿨쿨");
        }

        public abstract void makeSound();         // 다형성 지점 — 자식이 반드시 구현
    }

    class Dog extends Animal {
        Dog(String name) { super(name); }

        @Override
        public void makeSound() { System.out.println(name + ": 멍멍"); }
    }

    Animal a = new Dog("바둑이");
    a.sleep();       // 바둑이: 쿨쿨   ← 물려받은 공통 구현
    a.makeSound();   // 바둑이: 멍멍   ← 동적 바인딩으로 자식 구현 실행
    ```

    - `abstract` 메서드가 하나라도 있으면 클래스도 `abstract`여야 하고, **`new`로 직접 생성할 수 없음**
        + `new Animal("바둑이")` → 컴파일 에러. 오직 자식을 통해서만 객체가 됨
        + "미완성 설계도"라 그 자체로는 실체가 될 수 없다는 뜻
    - 반대로 `abstract` 메서드가 없어도 `abstract`를 붙일 수 있음 — 생성을 막는 용도

+ 인터페이스로 구현하는 다형성 — 클래스 상속은 하나지만 인터페이스는 여러 개 구현 가능 → **한 객체가 여러 타입으로 보일 수 있음**

    ```java
    class Duck extends Animal implements Swimmable, Flyable { ... }

    Animal    a = new Duck();   // 동물로 볼 때
    Swimmable s = new Duck();   // 헤엄치는 것으로 볼 때
    Flyable   f = new Duck();   // 나는 것으로 볼 때
    ```

    - 같은 객체를 **상황에 맞는 타입으로만** 노출할 수 있어서, 받는 쪽은 필요한 능력에만 의존하게 됨
    - 인터페이스 분리 원칙(ISP)과 의존 역전 원칙(DIP)이 코드에 실제로 드러나는 지점

+ `default` 메서드도 동적 바인딩됨 (Java 8+)
    - 구현 클래스가 재정의하면 재정의한 쪽이 실행됨. 일반 오버라이딩과 똑같이 동작

+ 충돌이 나면 컴파일러가 강제로 물어봄
    - 같은 시그니처의 `default` 메서드를 가진 인터페이스를 두 개 구현하면 **컴파일 에러**
    - 어느 쪽을 쓸지 직접 골라야 함 → `인터페이스명.super.메서드()`

    ```java
    interface A { default void hello() { System.out.println("A"); } }
    interface B { default void hello() { System.out.println("B"); } }

    class C implements A, B {
        @Override
        public void hello() {
            A.super.hello();   // 어느 쪽인지 명시해야 함
        }
    }
    ```

    - 클래스에 구현이 있으면 **클래스가 이김** (class wins) — 부모 클래스의 메서드가 인터페이스 `default`보다 우선
    - 자바가 다중 상속을 막으면서도 `default`를 허용할 수 있는 이유가 이 "충돌 시 컴파일 에러" 규칙임

+ 람다도 다형성의 한 형태
    - 추상 메서드가 하나뿐인 **함수형 인터페이스**는 구현 클래스를 만들지 않고 그 자리에서 구현할 수 있음

    ```java
    Shape circle = () -> System.out.println("Drawing Circle");
    circle.draw();   // 출력: Drawing Circle
    ```

+ 비교

    | 구분 | 추상 클래스 | 인터페이스 |
    |------|------------|-----------|
    | 키워드 | `abstract class` / `extends` | `interface` / `implements` |
    | **개수 제한** | **하나만** (단일 상속) | **여러 개** 구현 가능 |
    | 필드(상태) | ⭕ 인스턴스 필드 가능 | ❌ `public static final` 상수만 |
    | 생성자 | ⭕ 있음 (자식이 `super(...)`로 호출) | ❌ 없음 |
    | 구현 코드 | 일반 메서드로 제한 없이 | `default` · `static` · `private` 메서드만 (Java 8+) |
    | 접근 제어자 | 자유 (`protected` 등) | 메서드는 기본 `public` |
    | 결합도 | **강함** — 부모 구현에 묶임 | 느슨함 — 구현부가 없거나 얕음 |
    | 관계 | is-a (~의 한 종류다) | can-do (~을 할 수 있다) |

+ 실무에서 인터페이스가 더 널리 쓰이는 이유
    - ① **클래스는 하나만 상속할 수 있음** — 추상 클래스로 다형성을 쓰면 자식이 가진 **단 한 장의 상속 카드를 써버림**
        + 이미 다른 클래스를 상속 중이면 그 추상 클래스는 아예 쓸 수 없음
        + 인터페이스는 개수 제한이 없어서 이런 충돌이 생기지 않음

        ```java
        class Duck extends Animal implements Swimmable, Flyable, Comparable<Duck> { ... }
        //          └ 한 번뿐인 상속     └ 능력은 필요한 만큼 계속 붙일 수 있음
        ```

    - ② **서로 다른 계층에 같은 능력을 걸 수 있음**
        + `Bird`와 `Fish`는 공통 부모로 묶기 어렵지만 `Swimmable`은 양쪽에 다 붙일 수 있음
        + 상속 계층을 억지로 비틀지 않고도 공통 동작을 하나의 타입으로 다룰 수 있음
    - ③ **구현을 갈아끼우기 쉬움**
        + 받는 쪽이 인터페이스에만 의존하므로 구현체를 통째로 바꿔도 호출부는 그대로
        + 테스트에서 진짜 구현 대신 가짜 구현(mock)을 넣을 수 있는 것도 같은 이유
    - ④ **다이아몬드 문제에서 자유로움**
        + 상태를 갖지 않으니 여러 개 구현해도 "어느 부모의 필드냐" 문제가 생기지 않음
        + `default` 메서드 충돌은 위에서 본 것처럼 컴파일 에러로 잡아줌
    - ⑤ **표준 라이브러리부터가 인터페이스 중심**
        + `List`, `Map`, `Comparable`, `Runnable` 전부 인터페이스
        + `List<String> list = new ArrayList<>()`처럼 **인터페이스 타입으로 받아두는 것이 기본 습관**
    - 그래서 기본값은 **"일단 인터페이스로 두고, 공유할 상태나 구현이 실제로 생기면 그때 추상 클래스를 고려"**

+ 그래도 추상 클래스가 맞는 경우
    - 자식들이 **공통 필드(상태)** 를 가져야 할 때 — 인터페이스는 상수만 가능
    - **생성자로 초기화 규칙을 강제**하고 싶을 때 — 인터페이스에는 생성자가 없음
    - `protected`처럼 **자식에게만** 열어주는 멤버가 필요할 때
    - 공통 구현이 많고 자식은 **일부만 바꾸면 될 때** (템플릿 메서드 패턴)

    ```java
    abstract class Report {
        public final void print() {     // 전체 흐름은 부모가 고정 (final로 잠금)
            header();
            body();                     // 달라지는 부분만 자식에게 위임
            footer();
        }

        private void header() { System.out.println("=== 보고서 ==="); }
        private void footer() { System.out.println("=== 끝 ==="); }

        protected abstract void body();
    }
    ```

    - 인터페이스로는 "흐름을 고정하고 일부만 위임하는" 이 구조를 만들기 어려움

+ 실무에서는 **둘을 같이 쓰는 것**이 흔함
    - 타입은 인터페이스로 공개하고, 반복되는 구현은 **골격 구현(추상 클래스)** 으로 제공
    - 자바 표준 라이브러리가 그대로 이 구조임

    ```
    List (인터페이스)  ←  AbstractList (골격 구현)  ←  ArrayList (실제 구현)
    ```

    - 쓰는 쪽은 `List`에만 의존하고, 새 구현을 만드는 쪽은 `AbstractList`를 상속해 필요한 메서드만 채움
    - 인터페이스의 유연함과 추상 클래스의 코드 재사용을 둘 다 가져가는 방법

+ 고르는 기준 한 줄
    - "A는 B**이다**"면 추상 클래스, "A는 B를 **할 수 있다**"면 인터페이스
    - 애매하면 인터페이스 — 나중에 추상 클래스를 덧붙이는 건 쉽지만, 이미 써버린 상속 카드는 되돌리기 어려움

+ 개념 관점의 기본 비교는 [객체 지향이란 — 추상클래스 vs 인터페이스](../01-객체지향이란/객체지향이란.md#추상클래스-vs-인터페이스) 참고

### 배열과 제네릭의 다형성
+ 배열은 **공변(covariant)** — `Dog[]`를 `Animal[]`로 받을 수 있음
    - 편해 보이지만 타입 안전성이 깨져서 **런타임에 터짐**

    ```java
    Dog[] dogs = new Dog[3];
    Animal[] animals = dogs;   // 컴파일 OK (배열은 공변)
    animals[0] = new Cat();    // 컴파일 OK → 실행 시 ArrayStoreException
    // 실제 배열은 Dog[]인데 Cat을 넣으려 했기 때문
    ```

+ 제네릭은 **무공변(invariant)** — `List<Dog>`는 `List<Animal>`이 아님

    ```java
    List<Dog> dogs = new ArrayList<>();
    List<Animal> animals = dogs;   // ❌ 컴파일 에러
    ```

    - 불편해 보이지만 **의도된 설계**임. 위 배열 사례와 같은 사고를 컴파일 시점에 미리 막는 것
    - 제네릭 타입 정보는 실행 시점에 지워지므로(타입 소거) 런타임 검사에 기댈 수 없어서 컴파일러가 더 엄격하게 막는다

+ 그래도 여러 타입을 받고 싶으면 **와일드카드**를 씀

    ```java
    void makeAllSound(List<? extends Animal> animals) {   // Animal이거나 그 하위 타입의 리스트
        for (Animal a : animals) a.makeSound();           // 읽기 OK
        // animals.add(new Dog());                        // ❌ 쓰기는 막힘 (실제 원소 타입을 모르므로)
    }

    makeAllSound(List.of(new Dog(), new Dog()));   // List<Dog> 전달 가능
    ```

    - 읽기만 할 거면 `? extends`, 쓰기만 할 거면 `? super` (PECS: Producer-Extends, Consumer-Super)

### 다형성을 쓰는 이유
+ 핵심 효과는 **타입이 늘어나도 호출하는 쪽 코드가 바뀌지 않는 것**

    ```java
    // ❌ 다형성 없이 — 도형이 하나 늘 때마다 이 메서드를 고쳐야 함
    void drawAll(List<Object> shapes) {
        for (Object s : shapes) {
            if (s instanceof Circle) {
                ((Circle) s).drawCircle();
            } else if (s instanceof Square) {
                ((Square) s).drawSquare();
            }
            // Triangle이 생기면? 여기에 else if 추가... 이런 분기가 코드 곳곳에 흩어짐
        }
    }

    // ⭕ 다형성 — 새 도형이 생겨도 이 메서드는 그대로
    void drawAll(List<Shape> shapes) {
        for (Shape s : shapes) {
            s.draw();
        }
    }
    ```

    - 새 기능은 **새 클래스를 추가**해서 넣고 기존 코드는 건드리지 않음 → 개방-폐쇄 원칙(OCP)
    - 호출하는 쪽이 구현체가 아니라 **인터페이스에만 의존**하게 됨 → 의존 역전 원칙(DIP)
    - 자세한 원칙은 [객체지향 설계원칙](../02-객체지향-설계원칙/객체지향-설계원칙.md) 문서 참고

+ 표준 라이브러리 자체가 다형성으로 만들어져 있음
    - `List<String> list = new ArrayList<>()` → 나중에 `LinkedList`로 바꿔도 쓰는 코드는 그대로
    - `Object`의 `toString()`, `equals()`, `hashCode()`를 재정의하면 `println`, `HashMap`, `List.contains()`가 **알아서 내 구현을 부름**
        + 이 코드들은 대상을 `Object` 타입으로만 알고 호출하는데도 실제 객체의 구현이 실행되는 것 — 동적 바인딩이 없으면 불가능한 동작

+ 확장 지점으로 열 생각이 없다면 **막는 것도 설계**
    - `final` 클래스·메서드로 오버라이딩을 금지하면 동작이 바뀌지 않는다는 보장을 얻음
    - 다형성은 "열어두는" 선택이고, 열어둔 곳은 자식이 규칙을 깰 수 있다는 뜻이기도 함 (리스코프 치환 원칙)

### 자주 하는 착각
+ "업캐스팅하면 자식의 멤버가 사라진다"
    - 객체는 그대로 완전한 자식임. **컴파일러 시야에서만 가려지는 것**이라 다운캐스팅하면 다시 보임
+ "업캐스팅하면 부모 메서드가 실행된다"
    - 오버라이딩되어 있으면 **자식 구현이 실행됨**. 변수 타입은 "무엇을 부를 수 있는지"만 정하고 "무엇이 실행될지"는 못 정함
+ "다운캐스팅은 무조건 위험하다"
    - 실제 타입이 맞으면 안전함. 위험한 건 **확인 없이 하는 것**
+ "`instanceof`는 정확히 그 타입일 때만 `true`다"
    - 하위 타입이면 전부 `true`. 정확히 비교하려면 `getClass()`
+ "필드도 오버라이딩된다"
    - 필드는 하이딩임. 선언 타입 기준으로 결정되고, 부모·자식에 같은 이름이 있으면 한 객체 안에 **필드가 두 개** 존재함
+ "`static` 메서드도 다형성이 적용된다"
    - 하이딩임. 선언 타입 기준
+ "인터페이스 `default` 메서드는 재정의할 수 없다"
    - 재정의 가능하고, 재정의하면 동적 바인딩됨
+ "인터페이스는 구현 코드를 가질 수 없다"
    - Java 8부터 `default`·`static`, Java 9부터 `private` 메서드로 구현을 가질 수 있음. 다만 **상태(인스턴스 필드)는 여전히 못 가짐**
+ "추상 클래스는 `abstract` 메서드가 반드시 있어야 한다"
    - 없어도 됨. `abstract`만 붙여 **직접 생성을 막는 용도**로도 씀
+ "추상 클래스가 인터페이스보다 상위 개념이다"
    - 상하 관계가 아님. 상태·구현을 물려줄지(추상 클래스), 타입만 약속할지(인터페이스)의 선택일 뿐
+ "`List<Dog>`는 `List<Animal>`이다"
    - 아님. 제네릭은 무공변. 필요하면 `List<? extends Animal>`
+ "부모 타입으로 받으면 성능이 떨어진다"
    - 실측할 만한 차이가 아님. JIT가 실제 호출 대상을 관찰해 인라인함
