## 직렬화와 역직렬화

직렬화는 문법이 몇 줄 안 되지만, **실무에서 가장 조심해서 쓰라고 하는 기능**이기도 하다.
`implements Serializable` 한 줄이 클래스의 모든 필드를 공개 API로 만들고, 역직렬화는 생성자를 건너뛴 채 객체를 만들어내며, 신뢰할 수 없는 스트림을 읽는 것만으로 임의 코드가 실행될 수 있다.
여기서는 **어떻게 쓰는지**보다 **무엇이 위험하고 왜 대안을 쓰는지**까지 정리한다.

### 직렬화
+ 객체를 **바이트 스트림으로 변환**하여 파일 저장, 네트워크 전송 등에 사용할 수 있도록 하는 과정
+ 객체는 힙 위에 흩어진 참조들의 그래프라서 그대로는 파일에 쓸 수도, 소켓으로 보낼 수도 없음
    - 직렬화는 그 그래프를 **순서가 있는 1차원 바이트 열로 펴는 일**
+ 반대 과정이 역직렬화 — 바이트 스트림을 다시 객체 그래프로 복원
+ 쓰이는 자리
    - 파일·DB에 객체 상태 저장 (세션, 캐시)
    - 네트워크로 객체 전송 (RMI, 분산 캐시)
    - 프로세스가 재시작해도 살아남아야 하는 상태

### Serializable 인터페이스
+ `java.io.Serializable`은 **메서드가 하나도 없는 마커 인터페이스**
    - 구현할 게 없고, "이 클래스는 직렬화해도 된다"는 표시만 함
    - 실제 동작은 `ObjectOutputStream`이 리플렉션으로 필드를 읽어서 처리
+ 구현하지 않은 객체를 직렬화하려 하면 `NotSerializableException` (unchecked)

```java
import java.io.*;

class Person implements Serializable {          // Serializable 구현
    private static final long serialVersionUID = 1L;

    String name;
    int age;

    Person(String name, int age) {
        this.name = name;
        this.age = age;
    }
}
```

+ 직렬화 — `ObjectOutputStream`

    ```java
    try (ObjectOutputStream out =
             new ObjectOutputStream(new FileOutputStream("person.ser"))) {
        out.writeObject(new Person("Alice", 25));   // 객체 직렬화
    }
    ```

+ 역직렬화 — `ObjectInputStream`

    ```java
    try (ObjectInputStream in =
             new ObjectInputStream(new FileInputStream("person.ser"))) {
        Person p = (Person) in.readObject();        // 객체 역직렬화
    }
    ```

    - `readObject()`는 `ClassNotFoundException`(checked)과 `IOException`을 던짐
    - 스트림은 반드시 닫아야 하므로 try-with-resources를 쓰는 게 기본

### 무엇이 직렬화되고 무엇이 안 되나
+ **참조로 연결된 객체가 전부 따라 나감**
    - `Order`를 직렬화하면 그 안의 `Member`, `List<Item>`까지 전부 직렬화됨
    - 그 그래프 안에 `Serializable`이 아닌 객체가 하나라도 있으면 `NotSerializableException`
    - 필드 하나 추가했을 뿐인데 직렬화가 깨지는 이유가 이것
+ **`transient` — 이 필드는 빼라**

    ```java
    class Session implements Serializable {
        private String userId;
        private transient String password;      // 저장하지 않음
        private transient Connection conn;      // 직렬화 불가능한 자원
    }
    ```

    - 비밀번호·토큰 같은 민감 정보, `Connection`·`Thread`처럼 복원해도 의미 없는 자원에 붙임
    - 역직렬화하면 **기본값**으로 채워짐 (참조형 `null`, 숫자 `0`, `boolean` `false`)
    - 캐시처럼 다시 계산할 수 있는 값도 `transient`가 맞음
+ **`static` 필드는 대상이 아님**
    - 인스턴스가 아니라 **클래스에 속한 값**이라 인스턴스 상태가 아님
    - 역직렬화 후 보이는 값은 스트림에서 복원된 게 아니라 그 JVM에 이미 올라와 있던 값
+ 표준 라이브러리의 대부분은 직렬화 가능
    - `String`, 원시 래퍼, 배열, `ArrayList`, `HashMap`, `LocalDate` 등
    - ❌ `Optional`, `Stream`, 스레드·소켓·스트림 계열은 `Serializable`이 아님
        - `Optional`을 필드로 두지 말라는 이유 중 하나
    - ❌ 람다도 기본적으로 직렬화 불가 — `(Runnable & Serializable) () -> ...`처럼 캐스팅해야 하지만 권장되지 않음
+ **순환 참조는 무한 루프에 빠지지 않음**
    - `ObjectOutputStream`이 이미 쓴 객체를 핸들 테이블에 기록하고, 다시 만나면 **참조 번호만** 기록
    - 덕분에 A↔B 같은 순환도 처리되고, 같은 객체를 두 군데서 참조하면 역직렬화 후에도 같은 객체로 복원됨
    - ⚠️ 대신 함정 — 같은 스트림에 같은 객체를 다시 쓰면 **바뀐 값이 반영되지 않음**

        ```java
        out.writeObject(person);   // name = "Alice"
        person.name = "Bob";
        out.writeObject(person);   // ❌ 참조만 기록됨 → 읽으면 둘 다 "Alice"
        ```

        - `out.reset()`으로 핸들 테이블을 비워야 함

### serialVersionUID
+ 직렬화된 데이터와 클래스가 **같은 버전인지 확인하는 값**
+ 선언하지 않으면 컴파일러가 클래스 정보를 해싱해서 자동 생성
    - 클래스 이름, 구현 인터페이스, **필드뿐 아니라 메서드 시그니처·접근 제어자까지** 포함
    - 즉 **메서드 하나만 추가해도 값이 바뀜** → 기존 데이터를 `InvalidClassException`으로 전부 못 읽게 됨
    - 컴파일러 구현에 따라 값이 달라질 수도 있어서 더 위험
+ 그래서 `Serializable`을 구현하면 **반드시 명시적으로 선언**

    ```java
    private static final long serialVersionUID = 1L;
    ```

    - `private`으로 두는 이유 — 하위 클래스가 물려받으면 안 되므로 (각자 자기 값을 가져야 함)
    - 값 자체는 아무 숫자여도 상관없음. 중요한 건 **개발자가 통제한다는 것**
    - 호환을 깨는 변경을 했을 때만 값을 올려서 "이 데이터는 못 읽는다"고 명시적으로 선언
+ SUID가 같을 때 버전 간 호환성

    | 변경 내용 | 호환 | 결과 |
    |---|:--:|---|
    | 필드 추가 | ✅ | 옛 데이터를 읽으면 새 필드는 기본값 |
    | 필드 삭제 | ✅ | 스트림에 있는 값은 무시됨 |
    | 필드 이름 변경 | ⚠️ | 삭제 + 추가로 취급 → **값 유실** |
    | 필드 타입 변경 | ❌ | `InvalidClassException` |
    | 필드를 `transient`/`static`으로 | ⚠️ | 삭제와 동일 |
    | 메서드 추가·삭제 | ✅ | SUID를 명시했다면 영향 없음 |
    | 클래스·패키지 이름 변경 | ❌ | `ClassNotFoundException` |
    | 상속 계층 변경 | ❌ | `InvalidClassException` |

+ 이 표가 말해주는 것 — **직렬화되는 필드는 사실상 공개 API**
    - `private` 필드라도 이름을 바꾸는 순간 저장된 데이터가 깨짐
    - 리팩터링 자유도가 사라지는 것이 자바 직렬화의 가장 큰 비용

### 역직렬화는 생성자를 호출하지 않는다
+ 가장 많이 놓치는 지점 — 역직렬화는 **생성자를 거치지 않고** 객체를 만듦
    - JVM이 메모리만 할당하고 스트림에서 읽은 값을 필드에 직접 써넣음
    - 생성자에 넣어둔 **유효성 검사와 방어적 복사가 전부 우회됨**

    ```java
    class Age implements Serializable {
        private final int value;

        Age(int value) {
            if (value < 0) throw new IllegalArgumentException();  // 역직렬화는 여기를 안 지나감
            this.value = value;
        }
    }
    ```

    - 바이트를 조작한 스트림으로 `value = -1`인 `Age`를 만들 수 있음
    - `final` 필드도 리플렉션으로 채워지므로 막아주지 않음
+ 그래서 `readObject()`는 **또 하나의 public 생성자**로 취급해야 함
    - 커스텀 `readObject()` 안에서 직접 유효성 검사와 방어적 복사를 해야 함
+ 정확히는 — **직렬화 불가능한 최상위 부모 클래스의 no-arg 생성자**만 호출됨
    - 그 부모에 접근 가능한 기본 생성자가 없으면 `InvalidClassException`

### 상속과 직렬화
+ 부모가 `Serializable`이면 자식은 자동으로 직렬화 가능 (인터페이스는 상속됨)
+ 부모가 `Serializable`이 **아닌 경우**
    - 부모의 필드는 직렬화되지 않음 → 역직렬화 후 부모 필드는 **기본값**
    - 부모에 접근 가능한 no-arg 생성자가 없으면 `InvalidClassException`

    ```java
    class Base {                       // Serializable 아님
        int baseField;
        Base() { }                     // ✅ 이 생성자가 없으면 자식 역직렬화 실패
    }

    class Child extends Base implements Serializable {
        int childField;
    }
    // 역직렬화하면 childField는 복원되고, baseField는 0
    ```

+ 부모의 상태까지 살려야 하면 자식이 `writeObject`/`readObject`에서 직접 저장·복원해야 함

### 직렬화 커스터마이징
+ **`writeObject` / `readObject`** — 기본 동작을 유지하면서 앞뒤로 개입

    ```java
    class Member implements Serializable {
        private String name;
        private transient String secret;

        private void writeObject(ObjectOutputStream out) throws IOException {
            out.defaultWriteObject();           // 기본 필드 먼저 처리
            out.writeUTF(encrypt(secret));      // transient 필드를 직접 기록
        }

        private void readObject(ObjectInputStream in)
                throws IOException, ClassNotFoundException {
            in.defaultReadObject();             // 기본 필드 먼저 복원
            this.secret = decrypt(in.readUTF());
            if (name == null) throw new InvalidObjectException("name 필수");  // 유효성 검사
        }
    }
    ```

    - 시그니처가 정확히 `private void`여야 함. 오타가 나도 **컴파일 에러가 아니라 그냥 호출되지 않음**
    - 리플렉션으로 이름을 찾아 호출하는 구조라 IDE의 도움을 받기 어려움
+ **`writeReplace` / `readResolve`** — 스트림에 쓸 객체 / 역직렬화 결과 객체를 통째로 바꿔치기
    - `writeReplace`: 직렬화할 때 다른 객체(보통 가벼운 프록시)로 대체
    - `readResolve`: 역직렬화가 끝난 뒤 반환할 객체를 교체
+ **`Externalizable`** — 기본 동작을 전부 버리고 직접 다 씀
    - `writeExternal` / `readExternal`을 구현
    - **public no-arg 생성자 필수** — 역직렬화 시 이 생성자를 호출한 뒤 `readExternal`로 채움
    - 빠르고 크기도 작지만, 필드가 늘어날 때마다 손으로 관리해야 해서 실수가 나기 쉬움
+ **직렬화 프록시 패턴** — 커스터마이징이 필요하다면 대개 이게 가장 안전한 답

    ```java
    class Period implements Serializable {
        private final Date start, end;

        private Object writeReplace() {                  // 항상 프록시를 직렬화
            return new SerializationProxy(this);
        }

        private void readObject(ObjectInputStream in) throws InvalidObjectException {
            throw new InvalidObjectException("프록시가 필요합니다");  // 직접 역직렬화 차단
        }

        private static class SerializationProxy implements Serializable {
            private static final long serialVersionUID = 1L;
            private final Date start, end;

            SerializationProxy(Period p) { this.start = p.start; this.end = p.end; }

            private Object readResolve() {
                return new Period(start, end);           // ✅ 생성자를 통과 → 불변식 검증됨
            }
        }
    }
    ```

    - 역직렬화가 **정상 생성자를 거치게 만드는 것**이 핵심
    - `final` 필드를 유지할 수 있고, 바이트 조작 공격도 생성자에서 걸러짐

### 싱글턴과 역직렬화
+ 역직렬화는 **새 인스턴스를 만들기 때문에** 싱글턴이 깨짐

    ```java
    class Singleton implements Serializable {
        private static final Singleton INSTANCE = new Singleton();
        private Singleton() { }
        public static Singleton getInstance() { return INSTANCE; }
    }
    // 역직렬화하면 INSTANCE와 다른 객체가 하나 더 생김
    ```

+ `readResolve()`로 막을 수 있음

    ```java
    private Object readResolve() {
        return INSTANCE;                 // 새로 만들어진 객체는 버리고 원본 반환
    }
    ```

    - ⚠️ 이때 **인스턴스 필드는 전부 `transient`여야 함**
    - 아니면 `readResolve`가 실행되기 전에 만들어진 임시 객체의 참조를 훔쳐가는 공격이 가능
+ 가장 확실한 답은 **enum 싱글턴**

    ```java
    enum Singleton {
        INSTANCE;
        public void work() { }
    }
    ```

    - enum은 이름만 직렬화되고 복원은 JVM이 처리 → **인스턴스 유일성이 언어 차원에서 보장됨**
    - 리플렉션 공격에도 안전

### record의 직렬화 (Java 16+)
+ record는 직렬화 방식이 **일반 클래스와 다름**
    - 컴포넌트 값만 기록되고, 역직렬화는 **정규 생성자(canonical constructor)를 호출**함
    - 즉 컴팩트 생성자에 넣은 유효성 검사가 **역직렬화에서도 동작함**

    ```java
    record Age(int value) implements Serializable {
        Age {
            if (value < 0) throw new IllegalArgumentException();  // ✅ 역직렬화에서도 실행됨
        }
    }
    ```

+ `writeObject`, `readObject`, `readResolve` 같은 커스터마이징 훅은 **무시됨**
    - 리플렉션으로 필드를 직접 주무르는 통로 자체가 없어서 공격 표면이 훨씬 작음
+ 자바 직렬화를 꼭 써야 한다면 record가 가장 덜 위험한 선택지

### 역직렬화의 보안 문제
+ **핵심 — 캐스팅은 방어가 되지 않음**

    ```java
    Person p = (Person) in.readObject();   // ❌ 캐스팅은 readObject()가 끝난 뒤에 일어남
    ```

    - 스트림에 어떤 타입이 들어 있든 `readObject()`는 그 클래스를 로드하고 **그 클래스의 `readObject()`를 실행**함
    - 타입이 틀려서 `ClassCastException`이 나는 시점에는 이미 코드가 실행된 뒤
+ **가젯 체인 (gadget chain)**
    - 클래스패스에 있는 평범한 라이브러리 클래스들의 `readObject()`를 연쇄시켜 **임의 코드 실행**까지 끌고 가는 기법
    - Apache Commons Collections의 `InvokerTransformer`가 대표적인 사례이고, 페이로드를 자동 생성하는 도구(ysoserial)까지 공개되어 있음
    - 내 코드가 멀쩡해도 **의존성에 가젯이 하나만 있으면** 성립함
+ **역직렬화 폭탄 (deserialization bomb)**
    - 중첩된 `HashSet` 100단계 같은 구조는 스트림이 몇 KB밖에 안 되지만, 역직렬화하면 `hashCode()` 계산이 2^100번 필요해져서 서버가 멈춤
    - 크기 제한만으로는 막을 수 없는 DoS
+ **방어**
    - 1순위는 **신뢰할 수 없는 데이터를 자바 직렬화로 역직렬화하지 않는 것**. 나머지는 전부 차선책
    - `ObjectInputFilter` (Java 9+) — 허용 목록 방식으로 클래스·깊이·크기를 제한

        ```java
        ObjectInputFilter filter = ObjectInputFilter.Config.createFilter(
            "com.example.dto.*;java.base/*;maxdepth=10;!*");   // 마지막 !* 로 나머지 전부 거부
        in.setObjectInputFilter(filter);
        ```

        - JVM 전역으로는 `-Djdk.serialFilter=...`
        - Java 17+에는 스트림마다 다른 필터를 적용하는 필터 팩토리(JEP 415)도 있음
    - 민감 필드는 `transient`로 빼고, 꼭 필요하면 암호화해서 기록

### 자바 직렬화의 문제점과 대안
+ 자바 직렬화가 실무에서 기피되는 이유
    - **보안** — 역직렬화 자체가 공격 통로
    - **유지보수** — private 필드까지 공개 API가 되어 리팩터링이 막힘
    - **성능** — 리플렉션 기반이라 느리고, 클래스 메타데이터까지 실려 크기도 큼
    - **호환성** — 자바 전용. 다른 언어와 주고받을 수 없음
    - **디버깅** — 바이너리라 눈으로 확인이 안 됨
    - 깊은 객체 그래프는 재귀로 처리돼 `StackOverflowError`가 나기도 함
+ 대안 비교

    | 방식 | 형식 | 언어 간 호환 | 스키마 | 쓰는 자리 |
    |---|---|:--:|---|---|
    | 자바 직렬화 | 바이너리 | ❌ | 클래스 자체 | 레거시·RMI |
    | JSON (Jackson, Gson) | 텍스트 | ✅ | DTO | API 응답, 설정, 로그 — 사실상 기본값 |
    | Protobuf / Avro / Thrift | 바이너리 | ✅ | 별도 스키마 파일 | 서비스 간 통신, 대용량 메시지 |
    | Kryo / FST | 바이너리 | ❌ | 클래스 | 자바 전용 캐시 — JDK 직렬화보다 빠름 |

+ 선택 기준
    - 외부와 주고받는다 → **JSON**
    - 트래픽·용량이 중요하고 스키마를 관리할 수 있다 → **Protobuf/Avro**
    - 자바끼리 쓰는 내부 캐시 → Kryo, 또는 그래도 JSON
    - 자바 직렬화 → **기존 시스템과 맞춰야 할 때만**
+ 명시적인 DTO를 두고 변환하는 게 결국 가장 안전함
    - 도메인 객체의 필드 구조와 전송 포맷을 분리하면, 리팩터링해도 저장된 데이터가 깨지지 않음

### 실무에서 마주치는 자리
+ **JPA 엔티티의 `implements Serializable`**
    - 스펙상 준영속 엔티티를 전송할 수 있어야 하고 2차 캐시가 직렬화를 쓸 수 있어서 관례적으로 붙임
    - 복합 키 클래스(`@EmbeddedId`, `@IdClass`)는 **필수**이며 `equals`/`hashCode`도 함께 요구됨
+ **세션 클러스터링 / Redis 세션**
    - 스프링 세션의 기본 직렬화가 JDK 직렬화라, 클래스를 고치면 저장된 세션이 `InvalidClassException`으로 깨짐
    - JSON 직렬화로 바꾸는 설정을 권장하는 이유가 이것
+ **분산 캐시에 담는 객체**
    - 캐시에 넣는 순간 그 클래스의 필드 구조가 **배포 간 호환성 문제**가 됨
    - 캐시 전용 DTO를 따로 두면 도메인 클래스를 자유롭게 고칠 수 있음
+ **`serialVersionUID` 경고**
    - IDE가 띄우는 "serializable class has no definition of serialVersionUID" 경고는 무시하지 말 것

### 실무 기준
+ **신뢰할 수 없는 데이터는 자바 직렬화로 역직렬화하지 않는다**
    - 다른 어떤 규칙보다 우선함
+ **새로 만드는 코드에서는 자바 직렬화를 선택하지 않는다**
    - 기본은 JSON. 자바 직렬화는 기존 시스템과 맞춰야 할 때만
+ **`Serializable`을 구현했다면 `serialVersionUID`를 명시한다**
+ **직렬화되는 필드는 공개 API로 생각한다**
    - 이름·타입을 바꾸는 순간 저장된 데이터가 깨진다는 걸 전제로 설계
+ **민감 정보와 복원 불가능한 자원은 `transient`**
+ **커스터마이징이 필요하면 직렬화 프록시를, 싱글턴이면 enum을 먼저 고려한다**
+ **상속 계층에는 `Serializable`을 함부로 붙이지 않는다**
    - 하위 클래스 전체가 그 부담을 물려받음

### 자주 하는 착각
+ "`Serializable`만 붙이면 끝이다"
    - 그 순간부터 필드 구조가 **공개 API**가 되고 되돌리기 어려움
+ "`private` 필드는 직렬화되지 않는다"
    - 접근 제어자와 무관하게 전부 직렬화됨. 빼려면 `transient`
+ "`static` 필드도 저장된다"
    - 인스턴스 상태가 아니라 저장되지 않음. 복원 후 보이는 값은 그 JVM에 이미 있던 값
+ "역직렬화하면 생성자가 호출된다"
    - 호출되지 않음. 유효성 검사와 방어적 복사가 전부 우회됨
+ "`final` 필드는 역직렬화로 바뀔 수 없다"
    - 리플렉션으로 직접 채워지므로 `final`은 보호가 되지 않음
+ "캐스팅하니까 다른 타입이 오면 막힌다"
    - 캐스팅은 `readObject()`가 **끝난 뒤**에 일어남. 그전에 이미 코드가 실행됨
+ "`serialVersionUID`는 필드를 바꿀 때만 신경 쓰면 된다"
    - 명시하지 않으면 **메서드 추가만으로도** 자동 값이 바뀌어 기존 데이터를 못 읽음
+ "부모 클래스 필드도 알아서 저장된다"
    - 부모가 `Serializable`이 아니면 저장되지 않고, 기본 생성자가 없으면 예외까지 남
+ "순환 참조가 있으면 무한 루프에 빠진다"
    - 핸들 테이블로 처리됨. 오히려 문제는 **같은 객체를 다시 써도 갱신되지 않는 것**
+ "직렬화는 깊은 복사에 쓰기 좋다"
    - 동작은 하지만 느리고, 그래프 전체가 `Serializable`이어야 하며, `transient` 필드는 사라짐. 복사 생성자가 낫다
+ "JSON은 텍스트라 느려서 못 쓴다"
    - Jackson은 리플렉션 기반 자바 직렬화보다 대체로 빠름. 크기가 문제면 Protobuf로 가면 됨
