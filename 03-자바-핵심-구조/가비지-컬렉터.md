## 가비지 컬렉터

### 가비지 컬렉션 (Garbage Collection)
+ JVM이 필요하지 않은 객체를 자동으로 제거하여 메모리를 관리하는 기능
    - 프로그래머가 직접 메모리 해제를 하지 않아도 되도록 함
    - **힙 영역**에 존재하는 객체 중 더 이상 사용되지 않는 객체를 정리 대상으로 판단함
        + 힙에 있는 객체들은 언제까지 필요한지 예측하기 어려움
        + 반면, 스택에 있는 변수들은 메서드가 끝나면 자동으로 사라짐(수명이 명확)
+ GC가 관리하는 대상은 **메모리뿐임**
    - 파일, 소켓, DB 커넥션 같은 시스템 리소스는 GC가 닫아주지 않음
    - 리소스 해제는 try-with-resources 등으로 직접 처리해야 함

### 도달 가능성 (Reachability)
+ GC 대상 판단 기준
    - 루트 객체에서 시작해 참조를 따라가며, **도달할 수 없는 객체**만 가비지로 간주함
    - "참조가 없는 객체"가 아니라 "루트에서 도달할 수 없는 객체"임
+ 참조 카운팅(Reference Counting)을 쓰지 않는 이유
    - 참조 개수를 세는 방식은 **순환 참조**를 회수하지 못함
        + A가 B를, B가 A를 참조하면 외부에서 아무도 사용하지 않아도 카운트가 0이 되지 않음
    - 도달 가능성 방식은 루트에서 출발하므로 순환 참조 덩어리를 통째로 회수할 수 있음
+ 루트 객체(GC Root)의 예시
    - 스레드 스택에 있는 지역 변수 (메서드 내부 변수, 매개변수 등)
    - 로드된 클래스의 static 필드
        + JDK 8부터 static 필드의 **값**은 힙에 있는 Class 객체에 저장됨
        + Method Area의 구현체도 Metaspace(네이티브 메모리)로 이동함
    - JNI 글로벌 참조 (C/C++ 네이티브 코드에서 참조 중인 자바 객체)
    - 실행 중인 스레드 객체 자체
    - synchronized로 락이 걸려 있는 객체
    - JVM 내부에서 참조하는 객체 (시스템 클래스 로더, 예외 객체 등)

### GC 알고리즘
+ 아래 방식들은 모두 **추적(Tracing)** 방식에 속함
    - 루트에서 출발해 살아있는 객체를 따라가는 과정은 공통
    - 차이는 "찾아낸 다음에 무엇을 하는가"에 있음
+ Mark-Sweep
    - Mark: 루트에서 도달 가능한 객체에 표시
    - Sweep: 힙 전체를 훑으며 표시되지 않은 객체를 회수
    - 비용이 **전체 객체 수**에 비례함 (죽은 객체까지 모두 훑어야 하기 때문)
    - 회수된 자리가 흩어진 채로 남으므로 **메모리 단편화**가 발생
+ Mark-Compact
    - Mark 이후, 살아있는 객체를 한쪽으로 밀어 모아 단편화를 해소
    - 압축 비용이 추가되지만 연속된 빈 공간을 확보할 수 있음
+ Mark-Copy (Copying, Scavenge)
    - 살아있는 객체를 **비어 있는 영역으로 복사**하고, 원래 영역은 통째로 비움
        + 죽은 객체는 탐색조차 하지 않음
        + 복사하면서 차곡차곡 쌓이므로 압축이 자동으로 이루어짐 (별도 Compaction 단계가 없음)
    - 비용이 **살아있는 객체 수**에만 비례함
    - 전제 조건으로 복사해 넣을 빈 공간이 항상 확보되어 있어야 함
        + 힙의 일부를 비워 두어야 하므로 공간 효율은 낮음
    - 생존율이 낮은 영역(Young)에 압도적으로 유리함

### 영역별 알고리즘 적용
+ Young: **Mark-Copy**
    - 대부분 죽으므로 살아남은 소수만 복사하면 됨
    - Young 영역에는 Sweep 단계가 존재하지 않음
+ Old: 컬렉터마다 다름
    - Serial: Mark-Sweep-Compact
    - Parallel: Mark-Compact
    - CMS: Mark-Sweep (압축을 하지 않아 단편화 발생, JDK 14에서 제거됨)
    - G1: Mark-Copy (Old도 복사 방식으로 수집함)
+ 현재 기본 컬렉터인 G1은 Young/Old 모두 복사 방식이므로 Sweep 단계가 없음
+ GarbageCollectorMXBean에 표시되는 이름은 실제 알고리즘과 일치하지 않으므로 주의
    - Parallel Old의 이름은 "PS MarkSweep"이지만 실제 구현은 Mark-Compact 계열
    - 역사적 잔재이므로 이름만 보고 알고리즘을 판단하면 안 됨

### 약한 세대 가설 (Weak Generational Hypothesis)
+ 세대별 GC가 성립하는 전제
    - 대부분의 객체는 생성된 직후에 죽는다
    - 오래 살아남은 객체가 젊은 객체를 참조하는 경우는 드물다
+ 이 가설에 따라 힙을 Young / Old로 나누고 서로 다른 전략을 적용함
    - Young: 생존율이 낮음 → 자주, 빠르게, 복사 방식으로 수집
    - Old: 생존율이 높음 → 드물게, 비용을 감수하고 수집

### 힙 영역 구성
+ Young Generation
    - Eden: new로 생성한 객체가 처음 놓이는 곳
    - Survivor 0 / Survivor 1: Eden에서 살아남은 객체가 머무는 곳
+ Old Generation
    - Young에서 오래 살아남아 승격(Promotion)된 객체가 놓이는 곳
+ Metaspace
    - 클래스 메타데이터를 저장하는 영역으로, 힙이 아닌 **네이티브 메모리**에 위치
    - JDK 8에서 Permanent Generation을 대체함

### TLAB (Thread Local Allocation Buffer)
+ Eden을 스레드별 작은 청크로 나누어 할당하는 구조
+ 각 스레드가 자기 TLAB 안에서 포인터만 증가시켜 객체를 할당함 (bump-the-pointer)
    - 스레드 간 경합(lock)이 없어 객체 할당이 매우 빠름
+ TLAB 공간이 부족하면 새 TLAB을 할당받거나 Eden에 직접 할당함

### 객체 생존 흐름
+ Eden에 객체 생성
    - new로 생성한 객체는 대부분 Eden에 놓임
+ Young GC 발생
    - Eden이 꽉 차면 발생
    - **Eden + 현재 사용 중인 Survivor(From)** 의 생존 객체를 비어 있는 Survivor(To)로 복사
    - 복사가 끝나면 Eden과 From Survivor를 통째로 비움
    - From / To 역할은 매 GC마다 교대됨
+ Survivor가 두 개인 이유
    - 복사 방식은 "비어 있는 목적지"가 전제 조건이므로 항상 하나는 비어 있어야 함
    - S0 → S1 순서로 이동하는 것이 아니라, 두 영역이 From/To 역할을 번갈아 맡는 구조
+ age 증가
    - Survivor로 복사될 때마다 age(생존 횟수)가 1씩 증가함
+ Old로 승격 (Promotion)
    - age가 임계값을 넘으면 Old로 이동
        + -XX:MaxTenuringThreshold로 지정하며 기본값은 15
        + 실제로는 Survivor 점유율에 따라 JVM이 임계값을 동적으로 조정함
    - To Survivor에 자리가 없으면 age와 무관하게 Old로 밀려남
+ 조기 승격 (Premature Promotion)
    - Survivor가 좁으면 객체가 age를 채우지 못하고 Old로 넘어감
    - 금방 죽었을 객체가 Old에 쌓여 Old 수집이 잦아지는 원인이 됨

### Card Table과 Write Barrier
+ 문제: Young GC는 Young만 수집하는데, Old에 있는 객체가 Young 객체를 참조할 수 있음
    - 이 참조를 놓치면 살아있는 객체를 회수해 버리게 됨
    - 그렇다고 Old 전체를 스캔하면 Young GC가 빨라야 할 이유가 사라짐
+ 해결: Card Table
    - Old 영역을 일정 크기(HotSpot 기준 512바이트)의 카드로 나눈 요약 테이블
    - Old 객체가 Young 객체를 참조하게 되면 해당 카드를 dirty로 표시함
    - Young GC는 dirty로 표시된 카드에 해당하는 부분만 추가로 스캔하면 됨
+ Write Barrier
    - 참조를 대입하는 시점에 카드를 표시하도록 JIT이 삽입하는 짧은 코드
    - 이 덕분에 Old 전체를 뒤지지 않고도 Old → Young 참조를 추적할 수 있음
+ G1은 같은 목적으로 Remembered Set을 region 단위로 유지함

### Stop-the-World
+ GC 작업을 위해 애플리케이션 스레드를 모두 멈추는 현상
+ 정지 시간이 길수록 응답 지연으로 직결되므로 GC 튜닝의 핵심 지표가 됨
+ 최신 컬렉터일수록 작업을 애플리케이션과 동시에(concurrent) 수행해 정지 구간을 줄임

### GC 이름 정리
+ 실제 GC 로그에 찍히는 이름을 기준으로 이해하는 것이 정확함
    - Pause Young: Young 영역 수집
    - Pause Young (Mixed): Young 전체 + Old 일부 수집 (G1 전용)
    - Pause Full: 힙 전체 + Metaspace 수집, 가장 느림
+ Minor GC는 Young GC와 같은 말임
    - 고전적인 표현이며, JVM 로그에는 Minor라는 단어가 등장하지 않음
+ Major GC는 자료마다 의미가 다르므로 사용에 주의
    - Old 영역 수집을 가리키기도 하고, Full GC와 같은 뜻으로 쓰이기도 함
    - 이 역시 JVM 로그에는 등장하지 않는 용어임

### 컬렉터 종류
+ Serial GC
    - 단일 스레드로 수집하며 Stop-the-World가 김
    - 싱글 코어, 소규모 힙 환경용
+ Parallel GC
    - 여러 스레드로 수집하며 **처리량(Throughput) 중심**
    - JDK 8의 기본 컬렉터
+ CMS (Concurrent Mark Sweep)
    - 애플리케이션과 동시에 마킹하여 정지 시간을 줄임
    - 압축을 하지 않아 단편화가 누적되는 문제가 있음
    - JDK 9에서 deprecated, **JDK 14에서 제거됨**
+ G1 (Garbage First)
    - **JDK 9부터 기본 컬렉터**
    - 힙을 균일한 크기의 region으로 나누고, Young/Old를 region 단위로 관리함
        + Eden/Survivor/Old가 물리적으로 연속된 영역이 아님
        + region 크기는 1MB ~ 32MB 범위에서 결정됨
        + region 절반 이상을 차지하는 큰 객체는 Humongous로 분류되어 Old에 직접 할당됨
    - 쓰레기 비율이 높은 region부터 수집함 (Garbage First)
    - 목표 정지 시간을 지정할 수 있음
+ ZGC / Shenandoah
    - 힙 크기와 무관하게 정지 시간을 수 밀리초 이하로 유지하는 것이 목표
    - 마킹뿐 아니라 객체 이동(relocation)까지 애플리케이션과 동시에 수행함
    - **지연 시간(Latency) 중심**

### 컬렉터 선택 기준
+ 처리량(Throughput)과 지연 시간(Latency)은 트레이드오프 관계
    - 처리량: 전체 실행 시간 중 애플리케이션이 실제로 일한 시간의 비율
    - 지연 시간: 개별 GC로 인해 발생하는 정지 시간의 길이
+ 배치 처리처럼 총 처리 시간이 중요하면 처리량 중심 (Parallel)
+ API 서버처럼 응답 지연이 중요하면 지연 시간 중심 (G1, ZGC)
+ Old 수집과 Full GC를 최소화하는 것이 중요하다고 말하는 이유
    - Young GC와 달리 정지 시간이 길어 사용자 응답 지연으로 직결되기 때문
