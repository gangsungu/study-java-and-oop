## 자바의 접근 제어자

### 접근 제어자
+ 클래스, 메서드, 필드의 접근 범위를 제한하는 키워드
    - 캡슐화를 문법으로 강제하는 장치
    - 공개할 것과 감출 것을 나눠 변경의 영향 범위를 좁히는 것이 목적
+ 종류는 4가지이며 넓은 순서대로 public > protected > default > private
+ static, final, abstract는 접근 제어자가 아님
    - 접근 범위가 아니라 소속이나 확장 가능 여부를 정하는 제어자(modifier)
    - 접근 제어자와 함께 씀 (public static final 처럼)
+ 접근 제어자 별 특징
    - public
        + 어디서든 접근 가능
    - protected
        + 같은 패키지 + 다른 패키지의 자식 클래스
        + 다른 패키지의 자식에서는 조건이 붙음 (아래 "protected의 정확한 규칙" 참고)
    - default
        + 같은 패키지 내에서만 접근 가능
        + 아무것도 쓰지 않으면 default가 됨. `default`라는 키워드를 붙이는 것이 아님
            - 인터페이스의 `default` 메서드에 쓰는 default와는 완전히 다른 것
        + package-private 이라고도 부름
    - private
        + 같은 최상위 클래스 안에서만 접근 가능

### 접근 범위 정리
+ 패키지와 상속은 별개의 축이 아니라 겹치는 조건임
    - "같은 패키지"와 "자식 클래스"를 나란히 두면, 같은 패키지에 있는 자식 클래스가 어느 칸인지 정할 수 없음
    - 패키지로 먼저 나누고, 다른 패키지 안에서 자식인지 아닌지를 나눠야 정확함

    |접근 제어자|같은 클래스|같은 패키지|다른 패키지의 자식 클래스|다른 패키지의 그 외|
    |---|---|---|---|---|
    |public|✅|✅|✅|✅|
    |protected|✅|✅|⚠️ 조건부|❌|
    |default (아무것도 입력 안한 경우)|✅|✅|❌|❌|
    |private|✅|❌|❌|❌|

+ 자주 하는 착각
    - default는 상속과 무관함
        + 같은 패키지면 자식이 아니어도 접근되고, 다른 패키지면 자식이어도 접근되지 않음
    - protected는 상속 전용이 아님
        + 상속 관계가 없어도 같은 패키지면 접근됨. 즉 protected는 default보다 항상 넓음

### protected의 정확한 규칙
+ 다른 패키지의 자식 클래스에서는 자기 자신 타입(또는 그 하위 타입) 참조로만 접근 가능
    - 부모 타입 참조로는 접근할 수 없음
    - 자식이 물려받은 자기 몫만 건드리라는 의미. 같은 부모를 가진 남의 객체까지 열어주지는 않음

    ```java
    // pkg1
    public class Parent {
        protected void hello() {}
    }

    // pkg2
    public class Child extends Parent {
        void test(Parent p, Child c) {
            hello();        // OK (this.hello())
            super.hello();  // OK
            c.hello();      // OK (자기 타입 참조)
            p.hello();      // 컴파일 에러 (부모 타입 참조)
        }
    }
    ```
    - 형제 클래스(같은 부모를 상속한 다른 클래스) 타입으로도 접근할 수 없음
+ 같은 패키지 안에서는 이 제약이 없음
    - 패키지가 같으면 default 규칙만으로 이미 접근 가능하기 때문

### private의 정확한 범위
+ "그 클래스 안"이 아니라 "같은 최상위 클래스 안"임
    - 중첩 클래스와 바깥 클래스는 서로의 private 멤버에 접근할 수 있음
    - 파일이 아니라 최상위 클래스 기준. 한 파일에 있어도 최상위 클래스가 다르면 접근 불가

    ```java
    public class Outer {
        private int x = 1;

        static class Inner {
            private int y = 2;
            void read(Outer o) {
                System.out.println(o.x);   // OK
            }
        }

        void read(Inner i) {
            System.out.println(i.y);       // OK
        }
    }
    ```
+ JVM에는 원래 이 개념이 없었음
    - Java 10까지는 컴파일러가 `access$000` 같은 합성(synthetic) 메서드를 몰래 만들어 우회했음
    - Java 11의 Nestmates(JEP 181)부터 JVM이 중첩 관계를 인식해 직접 접근을 허용함

### 클래스에 붙이는 접근 제어자
+ 최상위 클래스에는 public과 default만 쓸 수 있음
    - private, protected는 컴파일 에러
    - 자신을 감싸는 클래스가 없어 private의 기준이 되는 범위 자체가 없기 때문
+ public 클래스는 파일명과 클래스명이 같아야 함
    - 한 파일에 public 최상위 클래스는 하나만 둘 수 있음
+ 중첩 클래스는 4가지 모두 사용 가능
    - 바깥 클래스의 멤버처럼 취급되기 때문

### 접근 제어자를 붙일 수 없는 곳
+ 지역 변수와 매개변수
    - 스택 프레임 안에서만 살아 있어 외부에서 접근할 방법 자체가 없음
    - 붙일 수 있는 제어자는 final 뿐

### 오버라이딩과 접근 제어자
+ 자식은 부모보다 접근 범위를 좁힐 수 없음
    - 같거나 더 넓게만 재정의할 수 있음
    - 부모의 public 메서드를 자식이 protected로 재정의하면 컴파일 에러
+ 좁히면 다형성이 깨지기 때문
    - 부모 타입 참조로 호출하던 코드가 자식 객체에서 갑자기 막히면 부모 자리에 자식을 넣을 수 없게 됨
    - 리스코프 치환 원칙(LSP)을 문법 차원에서 강제하는 규칙
+ private 메서드는 애초에 오버라이딩 대상이 아님
    - 자식에게 보이지 않으므로 같은 이름으로 만들어도 별개의 새 메서드가 됨
    - `@Override`를 붙여두면 이런 실수를 컴파일 에러로 잡을 수 있음

### 인터페이스 멤버의 접근 제어자
+ 인터페이스 멤버에는 암묵적인 접근 제어자가 붙음
    - 메서드: public abstract
    - 필드: public static final (상수만 선언 가능)
+ 구현 클래스에서 메서드를 public으로 쓰지 않으면 컴파일 에러
    - 인터페이스 메서드는 이미 public이므로 범위를 좁히는 것이 되기 때문
+ Java 9부터 인터페이스에 private 메서드를 둘 수 있음
    - default 메서드끼리 공통 로직을 빼내되 외부에는 노출하지 않기 위함

### 모듈 시스템과 public (Java 9+)
+ public이 더 이상 "정말 어디서나"를 뜻하지 않음
    - `module-info.java`에서 exports 하지 않은 패키지는 public이어도 모듈 밖에서 접근 불가
    - 라이브러리가 내부 구현 패키지를 감출 수 있게 됨
+ 모듈을 쓰지 않고 classpath로 실행하는 일반 애플리케이션에서는 기존과 동일하게 동작함

### 캡슐화 실무 기준
+ 가장 좁은 범위에서 시작해 필요할 때만 넓힘
    - 넓히는 것은 언제든 가능하지만, 이미 공개한 것을 좁히면 쓰던 쪽이 깨짐
+ 필드는 기본적으로 private
    - 값이 필요하면 메서드로 열어줌
    - getter/setter를 기계적으로 전부 만들면 private으로 둔 의미가 없어짐. 필요한 것만 만듦
+ protected 필드는 되도록 피함
    - 자식 클래스에 내부 구현이 그대로 노출되어 부모를 바꾸기 어려워짐
    - private 필드 + protected 메서드로 확장 지점만 열어주는 쪽이 안전함
+ 테스트 때문에 public으로 여는 것은 지양
    - 테스트를 같은 패키지에 두면 default 범위로 충분함
