## 자바 가상머신의 구조와 실행 매커니즘

### JVM (Java Virtual Machine)
+ 자바 프로그램을 실행하기 위한 가상 머신
+ 컴파일러가 만든 바이트 코드를 읽어 실제 동작을 수행하는 엔진
+ 운영체제와 독립적으로 동작하며 어떤 OS에서도 실행 가능

### 클래스 로더 (Class Loader)
+ 바이트 코드를 메모리에 로드하는 역할
+ 클래스 로딩 과정
    - 로딩 (적재)
        + 바이트 코드를 메모리(Method Area)에 적재하는 단계
        + 이 단계에서 코드가 실행되지는 않음
    - 링크 (연결)
        + 로드된 클래스의 코드와 데이터를 사용할 수 있도록 준비
    - 초기화 (초기화)
        + static 변수에 초기값을 할당하고 static 블록을 실행

### 런타임 데이터 영역 (Runtime Data Area)
+ JVM이 실행 중 사용하는 메모리 영역
    - Heap
        + 객체와 인스턴스 변수 저장
        + new 키워드로 생성하는 모든 객체들이 저장됨
        + 가비지 컬렉션의 대상
    - Stack
        + 메서드 호출 시 생성되는 메서드 정보 저장
        + 메서드 종료시 자동으로 제거되어 메모리 관리에 수월
        + 지역 변수, 매개 변수, 연산 결과 등 저장
    - Method Area
        + 클래스 정보, static 변수 저장
        + 클래스가 처음 로드될 때 한번만 올라감
    - PC Register
        + 현재 실행 중인 명령어의 주소 저장
        + 자바는 바이트 코드 명령어 단위로 실행되기 때문에 PC 레지스터를 통해 다음 실행할 명령어를 추적할 수 있음
    - Native Method Stack
        + 네이티브 코드(C, C++ 등) 실행 시 사용
+ 스택과 레지스터는 스레드마다 각각 독립적으로 생성됨
    - 별도의 실행 단위를 가지기 위함

### 실행 엔진 (Execution Engine)
+ JVM이 바이트코드를 실제 실행하는 역할
    - 최종적으로 기계어로 변환되어 CPU에서 실행됨
+ 실행 엔진의 내부 구조는 JVM 명세(JVMS)에 규정되어 있지 않음
    - 명세는 각 바이트 코드 명령어의 "의미"만 정의하고, 실행 방식은 구현체에 위임함
    - 아래 내용은 HotSpot JVM 기준
        + OpenJDK / Oracle JDK의 기본 구현
        + OpenJ9, GraalVM 등 다른 구현체는 구조가 다름
+ 가비지 컬렉터도 실행 엔진의 구성 요소로 분류하기도 함

### 인터프리터 (Interpreter)
+ 바이트 코드를 한 줄씩 읽고 실행
+ 컴파일 과정이 없어 빠르게 시작할 수 있음
    - 컴파일 과정이 없지만 기계어 번역을 하지않는 것은 아님
    - 영구적인 컴파일 결과물을 만들지 않기 때문에 컴파일 과정이 없다고 표현함
    - HotSpot은 템플릿 인터프리터(Template Interpreter) 방식을 사용함
        + 각 바이트 코드 명령어에 대응하는 기계어 조각을 JVM 시작 시 미리 생성해 둠
        + 실행 시에는 해당 조각을 찾아 실행하며, 매번 새로 번역하지 않음
+ 실행뿐 아니라 프로파일 정보 수집도 담당
    - 메서드 호출 횟수와 루프 반복(백엣지) 횟수를 카운팅
    - 특정 호출부에 실제로 어떤 타입이 전달되는지 기록
    - 이 정보가 JIT 컴파일의 입력이 됨
+ 단점: 같은 코드가 반복 실행될 때마다 다시 해석해야 함
    - 성능이 떨어질 수 있음

### JIT (Just-In-Time) 컴파일러
+ 반복 실행되는 바이트 코드를 기계어로 변환
    - 변환 결과는 코드 캐시(Code Cache)라는 별도 메모리 영역에 저장됨
    - 이후 호출 시에는 인터프리터를 거치지 않고 코드 캐시의 기계어로 바로 실행
    - 한 번 변환된 코드는 다시 변환하지 않음
+ JIT 컴파일러 자체는 코드를 실행하지 않음
    - 번역만 담당하며, 실행은 CPU가 코드 캐시의 기계어를 직접 수행
    - 실행을 담당하는 주체는 인터프리터
+ 런타임 정보를 활용하므로 정적 컴파일러보다 공격적인 최적화가 가능
    - 메서드 인라이닝, 반복문 최적화, 실제 타입에 기반한 가상 호출 최적화 등
+ 단점
    - 컴파일에 CPU와 메모리를 소모하고 코드 캐시 공간을 차지함
    - 최적화가 적용되기 전까지 워밍업(warm-up) 구간이 존재함
        + 컴파일은 별도의 컴파일러 스레드에서 백그라운드로 수행되므로 애플리케이션 실행 자체가 멈추지는 않음
        + 성능 측정 시 워밍업을 고려하지 않으면 결과가 왜곡됨

### 인터프리터와 JIT 컴파일러의 관계
+ 포함 관계가 아니라 대등한 관계
    - 실행 엔진 아래 나란히 존재하며 서로 협력함
+ 동작 순서
    - 인터프리터가 실행하면서 카운터를 누적
    - 임계치를 넘으면 해당 메서드를 컴파일 큐에 등록
    - 컴파일러 스레드가 백그라운드에서 기계어로 번역
        + 번역이 끝날 때까지 인터프리터는 계속 실행
    - 완료되면 메서드 진입점이 코드 캐시의 기계어로 교체됨
        + 이미 실행 중인 긴 루프는 OSR(On-Stack Replacement)로 도중에 전환됨
+ JIT 없이 실행은 가능하지만, 인터프리터 없이는 불가능
    - 인터프리터는 프로파일 공급원이자 역최적화 시의 대비책 역할을 하기 때문

### 계층형 컴파일 (Tiered Compilation)
+ 코드가 실행되는 빈도에 따라 최적화 수준을 단계적으로 높이는 방식
    - Level 0: 인터프리터
    - Level 1 ~ 3: C1 컴파일러
        + 빠르게 컴파일하지만 최적화 수준은 낮음
        + Level 1은 프로파일링 없음, Level 2는 제한적 프로파일링, Level 3은 전체 프로파일링
    - Level 4: C2 컴파일러
        + 컴파일에 시간이 오래 걸리지만 최적화 수준이 높음
+ 일반적인 전이 경로는 0 -> 3 -> 4
    - 컴파일 큐 상태나 메서드 형태에 따라 다른 경로도 발생함
+ 계층으로 나뉘어 있을 뿐 포함 관계는 아님
    - 자주 실행될수록 상위 계층으로 올라가고, 최적화 가정이 깨지면 하위로 내려옴

### 역최적화 (Deoptimization)
+ JIT은 수집된 프로파일에 기반한 "추측"으로 최적화를 수행함
    - 예: 특정 호출부에 항상 같은 타입만 전달된다고 가정하고 최적화
+ 가정이 깨지면 컴파일된 기계어를 폐기하고 인터프리터로 되돌아감
    - 실행 중이던 지점 그대로 인터프리터에서 이어서 실행됨
+ 주요 발생 원인
    - 예상하지 못한 타입이 전달된 경우
    - 실행되지 않을 것으로 가정해 생략했던 분기가 실제로 실행된 경우
    - 새로운 클래스가 로드되어 기존 클래스 계층 분석 결과가 무효화된 경우
+ 인터프리터가 단순히 "JIT 준비 전까지 쓰는 느린 수단"이 아님을 보여주는 근거

### 확인용 실행 옵션
+ -XX:+PrintCompilation
    - 어떤 메서드가 언제, 어떤 레벨로 컴파일되는지 출력
    - made not entrant 표시는 역최적화가 발생했음을 의미
+ -Xint
    - 인터프리터만 사용 (JIT 비활성화)
+ -XX:TieredStopAtLevel=1
    - C1까지만 사용 (C2 비활성화)

### 가비지 컬렉터 (Garbage Collector)
+ Heap 영역에서 사용하지 않는 객체를 자동으로 정리하여 메모리를 회수
+ 메모리 누수를 방지하고 효율적인 메모리 관리를 수행
+ 상세 내용은 [가비지 컬렉터](./가비지-컬렉터.md) 문서 참고
