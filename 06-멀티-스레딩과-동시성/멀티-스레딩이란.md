## 멀티 스레딩이란

### 프로세스와 스레드
+ 프로세스 (Process)
    - **실행 중인 프로그램** 하나
    - OS에게서 독립된 메모리 공간을 할당받음
    - 서로의 메모리를 침범할 수 없어 안전하지만, 통신하려면 IPC 같은 별도 수단이 필요해 비쌈
+ 스레드 (Thread)
    - 프로세스 **안에서 돌아가는 실행 흐름** 하나
    - 같은 프로세스의 스레드끼리는 **메모리를 공유**함
    - 생성·전환 비용이 프로세스보다 훨씬 싸고 데이터를 그냥 같이 쓸 수 있음
    - 대신 **공유하기 때문에 서로를 망가뜨릴 수 있음** (동시성 문제의 근원)
+ 자바 프로그램은 시작부터 이미 멀티 스레드
    - `main` 스레드가 `main()`을 실행하고, 뒤에서 GC 스레드 등이 같이 돌고 있음

    ```java
    System.out.println(Thread.currentThread().getName()); // 출력: main
    ```

### 멀티 스레딩이 필요한 이유
+ 왜 멀티 스레딩이 필요할까?
    - 작업을 순서대로 처리하면 하나 끝날 때까지 다음 작업을 못함
    - 예제처럼 sleep(1000)으로 1초씩 대기하는 작업이 3개라면 총 3초가 소요됨
    - 비효율적인 자원 사용 방식
        + sleep() 동안 스레드는 CPU를 놓고 아무 일도 하지 않음
        + 실제로는 DB 응답 대기, HTTP 호출 대기, 파일 읽기 대기가 이 자리를 차지함
    - 동시에 여러 작업을 처리하고 싶을 때는 멀티 스레딩이 필요함
+ 멀티 스레딩이란?
    - 하나의 프로그램에서 여러 작업(스레드)을 동시에 실행하는 것
    - 대기 시간이 많은 작업을 겹쳐서 처리할 수 있어 성능 향상 가능
        + CPU가 놀지 않고 다른 작업을 동시에 처리할 수 있음
    - 특히 네트워크, 파일 I/O, UI 등에서 자주 사용됨
        + 웹 서버가 요청마다 스레드를 배정하는 것도 같은 이유

    ```java
    public class Main {
        public static void main(String[] args) {
            task("작업 1");
            task("작업 2");
            task("작업 3");
        }

        public static void task(String name) {
            try {
                Thread.sleep(1000); // 1초 대기
                System.out.println(name + " 완료");
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
        }
    }

    ===== 출력 =====
    // 1초 뒤
    작업 1 완료
    // 2초 뒤
    작업 2 완료
    // 3초 뒤
    작업 3 완료
    ```

### 동시성과 병렬성
+ 자주 섞어 쓰지만 다른 개념

    | | 동시성 (Concurrency) | 병렬성 (Parallelism) |
    |---|---|---|
    | 의미 | 여러 작업을 **번갈아** 처리 | 여러 작업을 **같은 순간에** 처리 |
    | 조건 | 코어 1개로도 가능 | 코어가 여러 개여야 가능 |
    | 관심사 | 구조 — 어떻게 나눌 것인가 | 실행 — 얼마나 빨리 끝낼 것인가 |
    | 예 | 싱글 코어에서 스레드 10개 | 멀티 코어에서 병렬 스트림 |

+ 스레드를 만든다고 병렬 실행이 보장되는 건 아님
    - 스레드를 **어느 코어에 언제 올릴지는 OS 스케줄러가 결정**함
    - 그래서 실행 순서와 출력 순서는 매번 달라질 수 있음
+ 대기 시간이 긴 작업(I/O)은 동시성만으로도 이득이 큼
    - 어차피 기다리는 시간이라 코어가 하나여도 겹쳐 쓸 수 있기 때문

### 스레드가 공유하는 것과 아닌 것
+ 같은 프로세스의 스레드끼리

    | 영역 | 공유 여부 | 내용 |
    |---|:---:|---|
    | Heap | 공유 | `new`로 만든 모든 객체, 인스턴스 변수 |
    | Method Area | 공유 | 클래스 정보, `static` 변수 |
    | Stack | **고유** | 지역 변수, 매개 변수, 메서드 호출 정보 |
    | PC Register | **고유** | 현재 실행 중인 명령어 주소 |
    | Native Method Stack | **고유** | 네이티브 코드 실행 정보 |

+ 여기서 규칙이 하나 나옴
    - **지역 변수는 스레드마다 따로**라서 동시성 문제가 없음
    - **인스턴스 변수와 `static` 변수는 공유**라서 동시성 문제의 대상이 됨
+ 그래서 "이 값이 힙에 있나 스택에 있나"가 스레드 안전성을 판단하는 첫 기준이 됨

### 멀티 스레딩 구현 방법
+ Thread 클래스를 상속
    - Thread 클래스를 상속받아 run() 메서드를 오버라이딩하여 실행할 코드 작성
    - start() 메서드를 호출하면 새로운 스레드가 실행됨
        + run()을 직접 호출하면 멀티 스레딩이 되지 않으므로 반드시 start()를 호출해야 함
        + `start()`는 OS에 새 스레드를 요청하고, **그 스레드가** `run()`을 실행함
        + 같은 객체로 `start()`를 두 번 호출하면 `IllegalThreadStateException`이 남 (스레드는 재사용 불가)

        ```java
        class MyThread extends Thread {
            private String name;
            public MyThread(String name) {
                this.name = name;
            }

            @Override
            public void run() {
                try {
                    Thread.sleep(1000); // 1초 대기
                    System.out.println(name + " 완료");
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt(); // 인터럽트 상태 복원
                }
            }
        }

        public class Main {
            public static void main(String[] args) {
                Thread t1 = new MyThread("작업 1");
                Thread t2 = new MyThread("작업 2");
                Thread t3 = new MyThread("작업 3");

                t1.start();
                t2.start();
                t3.start();
                // main은 여기서 바로 끝나지만, JVM은 t1~t3가 끝날 때까지 종료되지 않음
            }
        }

        ===== 출력 =====
        // 1초 뒤 (동시에 실행)
        작업 1 완료
        작업 2 완료
        작업 3 완료
        // 출력 순서는 실행 시마다 달라질 수 있음
        ```

    - 단점이 뚜렷해서 실무에서는 거의 안 씀
        + 자바는 단일 상속이라 **다른 클래스를 상속할 여지가 사라짐**
        + "무슨 작업인가(run)"와 "어떻게 실행할까(Thread)"가 한 클래스에 붙어버림
+ Runnable 인터페이스를 구현
    - Thread를 상속받지 않고, Runnable 인터페이스를 구현
    - Thread 객체를 생성할 때 Runnable 객체를 전달하여 실행
    - Thread 상속 방식보다 유연하며, 다른 클래스도 동시에 상속 가능하므로 실무에서 더 많이 사용
        + **작업(Runnable)과 실행 수단(Thread)이 분리**되므로 스레드 풀에 그대로 넘길 수 있음

    ```java
    class MyRunnable implements Runnable {
        private String name;
        public MyRunnable(String name) {
            this.name = name;
        }

        @Override
        public void run() {
            try {
                Thread.sleep(1000); // 1초 대기
                System.out.println(name + " 완료");
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }
    }

    public class Main {
        public static void main(String[] args) {
            Thread t1 = new Thread(new MyRunnable("작업 1"));
            Thread t2 = new Thread(new MyRunnable("작업 2"));
            Thread t3 = new Thread(new MyRunnable("작업 3"));

            t1.start();
            t2.start();
            t3.start();
        }
    }

    ===== 출력 =====
    // 약 1초 뒤 (동시에 실행)
    작업 2 완료
    작업 3 완료
    작업 1 완료
    // 출력 순서는 매번 달라질 수 있음
    ```

    - `Runnable`은 추상 메서드가 하나뿐인 **함수형 인터페이스**라 람다로 줄일 수 있음

        ```java
        new Thread(() -> System.out.println("작업 완료")).start();
        ```
+ Executors 프레임워크 사용
    - ExecutorService를 사용하여 스레드를 효율적으로 관리
    - 스레드 개수를 자동으로 조절하며, 스레드 풀(Thread Pool) 기능을 제공
    - 직접 Thread를 생성하는 것보다 성능과 안정성이 뛰어남
        + 스레드를 **재사용**하므로 생성·소멸 비용이 사라짐
        + 동시 실행 스레드 수에 **상한**이 생겨 과부하로 죽는 상황을 막음
        + 작업 큐, 결과 반환, 종료 처리를 프레임워크가 담당

    ```java
    import java.util.concurrent.ExecutorService;
    import java.util.concurrent.Executors;

    public class Main {
        public static void main(String[] args) {
            ExecutorService executor = Executors.newFixedThreadPool(3); // 3개 스레드 사용
            Runnable task = () -> {
                try {
                    Thread.sleep(1000); // 1초 대기
                    System.out.println("스레드 실행: " +
                    Thread.currentThread().getName());
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            };

            for (int i = 0; i < 5; i++) {
                executor.execute(task); // 스레드 풀에서 스레드 실행
            }

            executor.shutdown(); // 스레드 풀 종료
        }
    }

    ===== 출력 =====
    // 약 1초 뒤 — 스레드가 3개뿐이라 3개만 먼저 처리됨
    스레드 실행: pool-1-thread-1
    스레드 실행: pool-1-thread-2
    스레드 실행: pool-1-thread-3
    // 약 2초 뒤 — 먼저 끝난 스레드가 남은 작업을 이어받음
    스레드 실행: pool-1-thread-1
    스레드 실행: pool-1-thread-2
    // 어떤 스레드가 재사용될지는 정해져 있지 않음
    ```

    - 작업 5개 중 3개만 먼저 도는 이유
        + 풀 크기가 3이라 나머지 2개는 **작업 큐에서 대기**하다가 자리가 나면 실행됨
        + 스레드 이름이 반복되는 것이 곧 **재사용**의 증거
+ 결과가 필요하면 Callable과 Future
    - `Runnable`은 반환값도 없고 체크 예외도 못 던짐
    - `Callable<T>`는 값을 반환하고 예외도 던질 수 있음
    - `submit()`이 돌려주는 `Future<T>`로 결과를 받음

    ```java
    ExecutorService executor = Executors.newFixedThreadPool(2);

    Future<Integer> future = executor.submit(() -> {
        Thread.sleep(1000);
        return 42;
    });

    System.out.println("다른 일 하는 중");  // 결과를 기다리지 않고 진행
    System.out.println(future.get());      // 여기서 결과가 올 때까지 블로킹 → 42

    executor.shutdown();
    ```

    - `Future.get()`은 **결과가 나올 때까지 호출한 스레드를 멈춤**
        + 던지자마자 `get()`하면 동기 호출과 다를 게 없음. 던져둘 걸 다 던지고 나중에 받아야 함
    - 여러 비동기 작업을 조합해야 하면 `CompletableFuture`가 더 적합

### 스레드 생명주기
+ `Thread.State`로 정의된 6가지 상태

    | 상태 | 언제 |
    |---|---|
    | `NEW` | 객체만 생성되고 아직 `start()` 전 |
    | `RUNNABLE` | 실행 중이거나 CPU를 받을 준비가 된 상태 |
    | `BLOCKED` | `synchronized` 락을 얻으려고 대기 |
    | `WAITING` | `wait()`, `join()`, `park()`로 무기한 대기 |
    | `TIMED_WAITING` | `sleep(n)`, `wait(n)`, `join(n)`으로 시간 제한 대기 |
    | `TERMINATED` | `run()`이 끝났거나 예외로 종료 |

+ 자바에는 `RUNNING` 상태가 따로 없음
    - "실제로 CPU에서 돌고 있음"과 "돌 준비가 됨"을 **둘 다 `RUNNABLE`로 묶음**
    - JVM 입장에서는 OS가 언제 코어에 올려주는지 알 수 없기 때문
+ `TERMINATED`가 되면 되돌릴 수 없음
    - 그래서 끝난 스레드에 `start()`를 다시 호출할 수 없음

### 스레드 제어
+ `join()` — 끝날 때까지 기다리기
    - 해당 스레드가 `TERMINATED`가 될 때까지 **호출한 쪽이 대기**
    - 각 스레드의 결과를 모아야 할 때 사용

    ```java
    t1.start();
    t2.start();
    t1.join();   // t1이 끝날 때까지 대기
    t2.join();   // t2가 끝날 때까지 대기
    System.out.println("모든 작업 완료");  // 반드시 마지막에 출력됨
    ```

+ `sleep()` — 정해진 시간만큼 멈추기
    - CPU는 놓지만 **가지고 있던 락은 그대로 쥐고 있음**
        + 락을 놓고 기다리는 건 `wait()`
    - 정확히 그 시간 뒤에 재개된다는 보장은 없음 (스케줄러가 다시 올려줘야 함)
+ `interrupt()` — 중단 "요청"
    - 스레드를 강제로 죽이는 게 아니라 **플래그를 세워 부탁**하는 것
    - 대상이 `sleep()`/`wait()`/`join()` 중이면 `InterruptedException`이 발생하며 깨어남
    - 계산 중이라면 아무 일도 안 일어나므로, 작업 쪽에서 직접 확인해야 함

    ```java
    while (!Thread.currentThread().isInterrupted()) {
        // 반복 작업
    }
    ```

+ `stop()`은 쓰면 안 됨
    - 락을 반납하지 않고 스레드를 죽여서 **공유 데이터가 깨진 상태로 남음**
    - 오래전부터 deprecated였고, Java 20부터는 호출 자체가 `UnsupportedOperationException`
+ 데몬 스레드
    - `setDaemon(true)`로 지정 (반드시 `start()` **전에** 호출)
    - **모든 사용자 스레드가 끝나면 JVM이 데몬 스레드를 기다리지 않고 종료**함
    - 로그 플러시, 캐시 정리 같은 보조 작업용. GC 스레드가 대표적인 예
    - 갑자기 끊겨도 되는 일에만 써야 함 (`finally`가 실행되지 않을 수 있음)

### InterruptedException을 삼키면 안 되는 이유
+ `catch`에서 `printStackTrace()`만 하고 넘어가는 코드가 흔하지만 위험함
    - `InterruptedException`이 던져지는 순간 **인터럽트 상태 플래그가 초기화**됨
    - 그대로 삼키면 상위 코드는 "중단 요청이 있었다"는 사실 자체를 알 수 없음
    - 결과적으로 종료 요청을 무시하고 계속 도는 스레드가 됨
+ 둘 중 하나로 처리해야 함

    ```java
    // 1. 그대로 던져서 호출자에게 알린다 (가능하면 이쪽)
    public void task() throws InterruptedException {
        Thread.sleep(1000);
    }

    // 2. 던질 수 없다면 (예: Runnable.run) 인터럽트 상태를 복원한다
    @Override
    public void run() {
        try {
            Thread.sleep(1000);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();  // 플래그 복원
            return;                              // 그리고 정리 후 빠져나온다
        }
    }
    ```

### 스레드 풀 다루기
+ `execute()`와 `submit()`의 차이

    | | `execute()` | `submit()` |
    |---|---|---|
    | 인자 | `Runnable` | `Runnable`, `Callable` |
    | 반환 | 없음 | `Future` |
    | 예외 | 그대로 올라가 `UncaughtExceptionHandler`로 감 | **`Future` 안에 담긴다** |

    - `submit()`의 예외는 `Future.get()`을 호출해야 `ExecutionException`으로 보임
        + `get()`을 안 하면 **예외가 조용히 사라짐** — 실무에서 자주 놓치는 함정
+ 종료 메서드
    - `shutdown()` — 새 작업만 거부하고, **이미 받은 작업은 끝까지 처리**
    - `shutdownNow()` — 큐에 남은 작업을 버리고 실행 중인 스레드에 `interrupt()`, 못 돌린 작업 목록 반환
    - `awaitTermination(t, unit)` — 실제로 다 끝났는지 기다리며 확인
        + `shutdown()`은 종료를 **요청**할 뿐 기다려주지 않음

    ```java
    executor.shutdown();
    if (!executor.awaitTermination(10, TimeUnit.SECONDS)) {
        executor.shutdownNow();
    }
    ```

    - Java 19+ 부터 `ExecutorService`가 `AutoCloseable`이라 try-with-resources로 대체 가능

        ```java
        try (ExecutorService executor = Executors.newFixedThreadPool(3)) {
            executor.execute(task);
        } // 블록을 벗어날 때 shutdown 후 종료까지 대기
        ```
+ 풀 크기를 정하는 기준
    - **CPU 바운드** (계산 위주) → 코어 수 또는 코어 수 + 1
        + 스레드를 더 늘려도 컨텍스트 스위칭만 늘어남
    - **I/O 바운드** (대기 위주) → 코어 수 × (1 + 대기 시간 / 작업 시간)
        + 대부분 기다리는 시간이라 코어 수보다 훨씬 크게 잡아도 됨
    - `Runtime.getRuntime().availableProcessors()`로 코어 수를 얻음
+ `Executors` 팩토리 메서드의 함정
    - `newFixedThreadPool()` — 작업 큐가 **무제한**이라 작업이 밀리면 큐가 쌓여 `OutOfMemoryError`
    - `newCachedThreadPool()` — 필요하면 **스레드를 무한히 생성**함
    - 그래서 운영 환경에서는 `ThreadPoolExecutor`를 직접 구성해 큐 크기, 최대 스레드 수, 거부 정책을 지정하는 편

### 가상 스레드 (Java 21+)
+ 기존 스레드(플랫폼 스레드)의 한계
    - 자바 스레드 1개 = OS 스레드 1개
    - 스택으로 기본 1MB 정도를 잡아서 **수만 개를 만들 수 없음**
    - I/O를 기다리는 동안 비싼 OS 스레드가 통째로 묶여 있음
+ 가상 스레드
    - JVM이 관리하는 가벼운 스레드. 수십만 개를 만들어도 됨
    - **블로킹되면 캐리어(플랫폼) 스레드를 반납**하고, 깨어날 때 다시 올라탐
    - 덕분에 "요청 하나에 스레드 하나"라는 단순한 코드를 그대로 두고도 처리량이 올라감

    ```java
    // 개별 생성
    Thread.startVirtualThread(() -> System.out.println("가상 스레드"));

    // 작업마다 가상 스레드를 하나씩 — 풀 크기를 고민할 필요가 없음
    try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
        for (int i = 0; i < 10_000; i++) {
            executor.submit(() -> { Thread.sleep(1000); return null; });
        }
    }
    ```

+ 주의할 점
    - **CPU 바운드 작업에는 이득이 없음**. 기다리는 시간이 있어야 반납할 게 생김
    - 가상 스레드는 **풀에 담아 쓰는 게 아니라 매번 새로 만드는 것**이 맞음 (생성이 싸기 때문)
    - Java 21에서는 `synchronized` 블록 안에서 블로킹되면 캐리어 스레드가 붙잡히는(pinning) 문제가 있어 `ReentrantLock`을 권장했으나, Java 24부터 해소됨

### 멀티 스레딩의 비용
+ 스레드를 늘린다고 항상 빨라지지 않음
    - **컨텍스트 스위칭** — 코어 수보다 스레드가 많으면 번갈아 올리느라 오버헤드가 생김
    - **메모리** — 플랫폼 스레드는 스택으로 기본 1MB 정도를 차지함
    - **생성 비용** — OS 스레드를 만드는 일이라 싸지 않음. 그래서 풀을 씀
+ 코드가 어려워짐
    - 실행 순서가 정해져 있지 않아 **버그가 재현되지 않음**
    - 로컬에서 잘 되던 코드가 부하가 걸릴 때만 깨지는 일이 흔함
+ 그래서 순서를 지켜 판단하는 편
    - 이 작업이 **정말 대기 시간이 긴가**(I/O) → 그렇다면 이득이 큼
    - 단순히 계산이 오래 걸린다면 → 알고리즘부터 개선
    - 공유 상태가 있는가 → 있다면 동기화 비용까지 계산에 넣어야 함

### 여기서 생기는 문제
+ 스레드가 메모리를 공유한다는 사실에서 문제가 시작됨

    ```java
    class Counter {
        private int count = 0;
        public void increment() { count++; }   // 실제로는 읽기 → 더하기 → 쓰기 3단계
        public int getCount() { return count; }
    }

    // 스레드 2개가 각각 10000번씩 increment()
    // 기대: 20000
    // 실제: 13847, 17203 ... 매번 다름
    ```

+ 세 가지 축으로 나뉨
    - **원자성 (Atomicity)** — `count++`처럼 여러 단계인 연산이 중간에 끼어들기를 당함
    - **가시성 (Visibility)** — 한 스레드가 바꾼 값이 다른 스레드에 안 보일 수 있음 (CPU 캐시, JIT 최적화)
    - **순서 (Ordering)** — 컴파일러와 CPU가 성능을 위해 명령 순서를 바꿈
+ 해결 수단은 `synchronized`, `volatile`, `Atomic` 계열, `Lock`, 동시성 컬렉션 등
    - 분량이 커서 별도 문서로 정리 예정

### 자주 하는 착각
+ "`run()`을 호출해도 스레드가 실행된다"
    - 새 스레드가 생기지 않고 **호출한 스레드에서 그냥 메서드가 실행**됨. 순차 실행과 동일
+ "`start()`를 다시 호출하면 스레드를 재사용할 수 있다"
    - `IllegalThreadStateException`이 남. 끝난 스레드는 되살릴 수 없어서 **재사용하려면 스레드 풀을 써야 함**
+ "스레드를 많이 만들수록 빨라진다"
    - 코어 수를 넘어서면 컨텍스트 스위칭 비용이 이득을 깎아먹음. CPU 바운드 작업은 오히려 느려짐
+ "`sleep()`은 락을 반납한다"
    - 반납하지 않음. 락을 쥔 채 잠들기 때문에 다른 스레드는 계속 기다림. 락을 놓는 건 `wait()`
+ "`interrupt()`를 호출하면 스레드가 멈춘다"
    - 플래그를 세울 뿐임. 대기 중이 아니면 아무 일도 일어나지 않고, 작업 쪽에서 확인해야 멈춤
+ "`shutdown()`을 호출하면 스레드 풀이 즉시 종료된다"
    - 이미 받은 작업은 다 끝냄. 실제로 끝났는지 확인하려면 `awaitTermination()`이 필요함
+ "`submit()`으로 던진 작업에서 예외가 나면 로그에 찍힌다"
    - `Future`에 담겨서 **아무 소리 없이 사라짐**. `get()`을 호출해야 `ExecutionException`으로 드러남
+ "`main`이 끝나면 프로그램이 끝난다"
    - 사용자 스레드가 하나라도 살아 있으면 JVM은 종료되지 않음. 데몬 스레드만 남았을 때 종료됨
+ "지역 변수도 동기화해야 한다"
    - 지역 변수는 **스레드마다 별도의 스택**에 있어 공유되지 않음. 문제가 되는 건 인스턴스 변수와 `static` 변수
+ "가상 스레드를 쓰면 무조건 빨라진다"
    - 블로킹 I/O가 있어야 이득이 있음. CPU 바운드 작업에서는 차이가 없거나 오히려 손해
