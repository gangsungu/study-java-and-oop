### A. 객체지향의 특징 (추상화 · 캡슐화 · 상속 · 다형성)

#### A-1. 🟢
추상화와 캡슐화는 둘 다 "숨긴다"는 말로 설명되곤 합니다.
**두 개념이 각각 무엇을 숨기는지** 구분해서 한 문장씩 서술하세요.

<details><summary>답 보기</summary>

- **추상화**는 *복잡함*을 숨긴다. 대상이 가진 수많은 특성 중 문제 해결에 필요한 것만 남기고 나머지를 버려서, 사용하는 쪽이 본질만 보게 한다. (동물의 체온·유전자·털 개수를 다 버리고 `name`, `speak()`만 남김)
- **캡슐화**는 *내부 구현과 상태*를 숨긴다. 데이터를 외부에서 직접 건드리지 못하게 막고 정해진 통로(메서드)로만 접근시켜, 객체가 항상 올바른 상태를 유지하도록 보장한다.

한 줄 정리: 추상화는 **"무엇을 보여줄 것인가(설계 관점)"**, 캡슐화는 **"어떻게 보호할 것인가(구현 관점)"**.

</details>

#### A-2. 🟡
"캡슐화 = 필드를 `private`으로 만들고 모든 필드에 getter/setter를 만드는 것"이라고 배우는 경우가 많습니다.
이 설명이 왜 **캡슐화의 취지를 깨뜨릴 수 있는지** 설명하고, 개선 방향을 제시하세요.

<details><summary>답 보기</summary>

모든 필드에 setter를 기계적으로 뚫으면 `private`을 붙였을 뿐 외부에서 상태를 마음대로 바꿀 수 있다는 점은 `public` 필드와 다를 게 없다. **접근 제어자는 형식이고, 캡슐화의 본질은 "객체가 자기 상태의 정합성을 스스로 책임지는 것"** 이다.

개선 방향:
1. **setter를 기본으로 만들지 않는다.** 정말 외부에서 바꿔야 하는 값만 연다.
2. **setter 대신 의미 있는 행위 메서드**를 제공한다. `account.setBalance(b - 1000)` 대신 `account.withdraw(1000)` — 잔액 부족 검증을 객체가 직접 한다.
3. 열어야 한다면 **검증을 넣는다.** (`Ex01_OopBasics`의 `setAge()`가 음수를 막는 방식)
4. 바뀔 필요가 없는 값은 `final` + 생성자 주입으로 **불변**으로 만든다.

</details>

#### A-3. 🟡
다형성이 **없다고 가정**하고, 여러 종류의 동물이 담긴 목록을 순회하며 각자의 소리를 출력하는 코드를 어떻게 작성해야 할지 서술하세요.
그리고 그 방식에서 **새로운 동물(예: `Cow`)을 추가할 때** 무엇이 문제가 되는지 설명하세요.

<details><summary>답 보기</summary>

다형성이 없다면 순회하면서 타입을 일일이 검사하는 분기가 필요하다.

```java
for (Object animal : zoo) {
    if (animal instanceof Cat)       ((Cat) animal).meow();
    else if (animal instanceof Dog)  ((Dog) animal).bark();
    else if (animal instanceof Duck) ((Duck) animal).quack();
}
```

`Cow`를 추가할 때의 문제:
- **기존 코드를 고쳐야 한다.** `else if` 한 줄을 추가해야 하므로 이미 검증된 코드에 손을 대게 되고, 이는 OCP(개방-폐쇄 원칙) 위반이다.
- **고쳐야 할 곳이 한 군데가 아니다.** 소리 내기·먹이 주기·재우기마다 똑같은 분기가 흩어져 있다면 전부 찾아 수정해야 하고, **하나라도 빠뜨리면 컴파일은 통과하고 런타임에 조용히 누락**된다.

다형성을 쓰면 `Cow extends Animal`을 만들고 `speak()`만 구현하면 끝이며, 순회 코드는 그대로다. → `Ex01_OopBasics.java`의 3번 항목

</details>

#### A-4. 🔴
상속은 "코드 재사용"의 대표적인 수단으로 소개되지만, 실무에서는 **"상속보다 합성(composition)을 선호하라"** 는 조언이 널리 쓰입니다.
상속을 코드 재사용 목적으로만 남용하면 어떤 문제가 생기는지 서술하세요.

<details><summary>답 보기</summary>

1. **강한 결합**: 자식은 부모의 구현 세부사항에 묶인다. 부모가 내부적으로 자기 메서드를 호출하는 방식만 바꿔도 자식이 조용히 망가진다(취약한 기반 클래스 문제).
2. **캡슐화 위반**: `protected` 멤버를 통해 자식이 부모의 내부를 들여다보게 되어, 부모는 마음대로 리팩터링할 수 없다.
3. **잘못된 관계 모델링**: 코드를 재사용하려고 `Stack extends ArrayList` 같은 상속을 하면, `Stack`이 `add(0, x)` 같은 스택과 무관한 연산을 물려받아 **불변식이 깨진다.** is-a 관계가 아닌데 상속한 결과다.
4. **단일 상속의 낭비**: 자바는 클래스를 하나만 상속할 수 있는데, 그 한 자리를 단순 재사용에 써버리면 정작 필요한 상속을 못 한다.

판단 기준: **"자식이 부모의 모든 것을 대체할 수 있는가(리스코프 치환)"** 를 물어보고, 아니라면 필드로 가지고 위임하는 합성을 쓴다.

</details>

### B. 상속과 생성자 규칙

#### B-1. 🟢 출력 예측
```java
class A {
    A()      { System.out.println("A"); }
    A(int x) { System.out.println("A" + x); }
}
class B extends A {
    B()      { this(10); System.out.println("B"); }
    B(int x) { super(x); System.out.println("B" + x); }
}
// new B(); 실행
```
출력 결과를 순서대로 쓰고, **`A()`(인자 없는 생성자)가 왜 실행되지 않는지** 설명하세요.

<details><summary>답 보기</summary>

```
A10
B10
B
```

`B()`의 첫 줄이 `this(10)`이다. **생성자 첫 줄에는 `super(...)`나 `this(...)` 중 하나만 올 수 있고**, `this(...)`를 썼으므로 `super()` 자동 삽입은 일어나지 않는다. 제어는 `B(int)`로 넘어가고 거기서 `super(x)`가 `A(int)`를 호출한다. 즉 부모 생성자는 `A(int)` 하나만 실행되며, `A()`는 호출될 기회가 없다.

**부모 생성자는 객체 하나당 정확히 한 번만 실행된다**는 점이 핵심이다.

</details>

#### B-2. 🟢
아래 코드는 컴파일 에러가 납니다. **원인**을 정확히 서술하고 **해결 방법 3가지**를 코드로 제시하세요.
```java
class Animal {
    public Animal(String name) { }
}
class Cat extends Animal {
    public Cat() { }
}
```

<details><summary>답 보기</summary>

**원인**: `Animal`이 생성자를 하나라도 직접 선언했기 때문에 컴파일러는 더 이상 기본 생성자 `Animal()`을 만들어주지 않는다. 한편 `Cat()`의 첫 줄에는 `super(...)`도 `this(...)`도 없으므로 컴파일러가 **인자 없는 `super()`를 자동으로 삽입**하는데, 호출할 `Animal()`이 존재하지 않아 에러가 난다.

> `constructor Animal in class Animal cannot be applied to given types; required: String, found: no arguments`

**해결 3가지**
```java
// ① 부모에 기본 생성자를 추가
class Animal {
    public Animal() { }
    public Animal(String name) { }
}

// ② 자식이 부모 생성자를 직접 호출
class Cat extends Animal {
    public Cat() { super("이름 없음"); }
}

// ③ 같은 클래스의 다른 생성자를 경유
class Cat extends Animal {
    public Cat()            { this("이름 없음"); }
    public Cat(String name) { super(name); }
}
```
실제 에러 메시지 확인: `javac 01-객체지향이란/examples/errors/Err01_MissingSuper.java`

</details>

#### B-3. 🟡
"생성자 첫 줄에는 `super(...)`와 `this(...)` 중 **하나만**, 그것도 **첫 줄에만**" 올 수 있습니다.
자바가 이런 제약을 두는 이유를 설명하세요.

<details><summary>답 보기</summary>

**부모가 완전히 초기화되기 전에는 자식의 코드가 절대 실행되면 안 되기 때문**이다.

- 자식은 부모의 필드를 물려받아 사용한다. 부모 초기화 전에 자식 로직이 돌면 부모 필드가 아직 기본값(`null`/`0`)인 상태에서 동작하게 된다.
- 그래서 부모 생성자 호출은 **반드시 맨 처음**이어야 하고, 자바는 이를 문법으로 강제한다.
- 둘 다 쓸 수 없는 이유는 **부모 생성자가 두 번 실행되는 것을 막기 위해서**다. `this(...)`로 넘어간 생성자가 결국 `super(...)`를 호출하므로, 부모 초기화는 어느 경로로든 정확히 한 번만 일어난다.

(참고: Java 22부터는 `super()` 앞에 부모와 무관한 검증 코드를 둘 수 있게 완화되었지만, "부모 초기화 전 자식 필드 접근 금지"라는 원칙 자체는 그대로다.)

</details>

#### B-4. 🟡 출력 예측
```java
class Parent {
    public Parent() { print(); }
    public void print() { System.out.println("Parent.print"); }
}
class Child extends Parent {
    private String message = "초기화 완료";
    public Child() { print(); }
    @Override public void print() { System.out.println("Child.print: " + message); }
}
// new Child(); 실행
```
출력을 예측하고 **왜 그런 결과가 나오는지** 설명하세요. 이 코드에서 얻을 교훈은 무엇인가요?

<details><summary>답 보기</summary>

```
Child.print: null
Child.print: 초기화 완료
```

이유:
1. `Child()`의 `super()`가 먼저 실행되어 `Parent()` 안에서 `print()`가 호출된다.
2. **동적 바인딩** 때문에 `Parent.print()`가 아니라 `Child.print()`가 실행된다. 실제 객체가 `Child`이기 때문이다.
3. 그런데 이 시점은 부모 생성자가 도는 중이고, **자식의 필드 초기화(`message = "초기화 완료"`)는 부모 생성자가 끝난 뒤에 일어난다.** 그래서 `message`는 아직 `null`이다.

**교훈: 생성자 안에서는 오버라이드 가능한 메서드를 호출하지 말 것.** 꼭 호출해야 한다면 `private`, `static`, 또는 `final` 메서드로 만들어 재정의를 원천 차단한다.
직접 실행: `java 01-객체지향이란/examples/Ex02_ConstructorRules.java`

</details>

#### B-5. 🔴 출력 예측
```java
class Parent {
    static { System.out.println("1. Parent static 블록"); }
    { System.out.println("2. Parent 인스턴스 블록"); }
    Parent() { System.out.println("3. Parent 생성자"); }
}
class Child extends Parent {
    static { System.out.println("4. Child static 블록"); }
    { System.out.println("5. Child 인스턴스 블록"); }
    Child() { System.out.println("6. Child 생성자"); }
}
// new Child(); 를 두 번 실행
```
출력을 모두 쓰고, 두 번째 생성 때 결과가 달라지는 이유를 설명하세요.

<details><summary>답 보기</summary>

```
--- 첫 번째 ---
1. Parent static 블록
4. Child static 블록
2. Parent 인스턴스 블록
3. Parent 생성자
5. Child 인스턴스 블록
6. Child 생성자
--- 두 번째 ---
2. Parent 인스턴스 블록
3. Parent 생성자
5. Child 인스턴스 블록
6. Child 생성자
```

**초기화 순서**: static 블록(부모→자식, 클래스 로딩 시 **딱 한 번**) → 인스턴스 블록 & 필드 초기화(부모) → 부모 생성자 → 인스턴스 블록 & 필드 초기화(자식) → 자식 생성자

두 번째부터 `1`, `4`가 안 나오는 이유는 **static 블록이 클래스당 한 번, 클래스가 최초로 로딩될 때만 실행**되기 때문이다. 인스턴스 관련 초기화는 객체를 만들 때마다 반복된다.

한 문장 정리: **"클래스는 한 번, 인스턴스는 매번. 둘 다 부모가 먼저."**

</details>

### C. 다형성

#### C-1. 🟢
`Animal a = new Cat("나비");` 이후 `a.scratch()`(Cat에만 있는 메서드)는 컴파일 에러이지만, `a.speak()`는 Cat의 것이 실행됩니다.
이 두 현상을 **하나의 원칙**으로 묶어 한 문장으로 설명하세요.

<details><summary>답 보기</summary>

**"무엇을 호출할 수 있는지는 선언 타입이 결정하고, 그 호출이 실제로 어떻게 동작하는지는 실제 객체가 결정한다."**

- 컴파일러는 변수의 **선언 타입(`Animal`)** 만 보고 그 타입에 그 메서드가 있는지 검사한다 → `scratch()`는 `Animal`에 없으므로 컴파일 실패.
- 실행 시점에는 JVM이 **실제 객체(`Cat`)** 의 메서드 테이블을 보고 재정의된 버전을 호출한다 → `speak()`는 Cat 것이 실행(동적 바인딩).

</details>

#### C-2. 🟡 출력 예측
```java
public class Q {
    public static void main(String[] args) {
        Animal a = new Dog();
        Dog    d = new Dog();
        check(a);
        check(d);
        a.sound();
        System.out.println(a.legs + " / " + d.legs);
    }
    static void check(Animal x) { System.out.println("check(Animal)"); }
    static void check(Dog x)    { System.out.println("check(Dog)"); }
}
class Animal {
    int legs = 4;
    void sound() { System.out.println("..."); }
}
class Dog extends Animal {
    int legs = 999;
    @Override void sound() { System.out.println("멍멍"); }
}
```
출력 4줄을 예측하고, `a`와 `d`가 **똑같이 `Dog` 객체인데도** 결과가 갈리는 지점을 설명하세요.

<details><summary>답 보기</summary>

```
check(Animal)
check(Dog)
멍멍
4 / 999
```

- **`check(a)` vs `check(d)`**: 오버로딩은 **컴파일 타임에 선언 타입으로** 결정된다(정적 바인딩). 둘 다 `Dog` 객체지만 `a`의 선언 타입이 `Animal`이므로 `check(Animal)`이 선택된다.
- **`a.sound()`**: 오버라이딩은 **런타임에 실제 객체로** 결정된다(동적 바인딩) → `"멍멍"`.
- **`a.legs`가 4**: **필드는 오버라이딩되지 않는다.** 자식의 `legs`는 부모의 것을 가릴 뿐(field hiding), 두 필드가 각각 존재하며 **선언 타입을 따라 선택**된다.

정리: **재정의되는 것은 오직 인스턴스 메서드뿐.** 필드와 static 메서드는 선언 타입을 따라간다. 그래서 상태는 반드시 메서드(getter)로 접근해야 한다.

</details>

#### C-3. 🟡 출력 예측
```java
Parent p = new Child();
p.staticM();
p.instanceM();
```
`Parent`와 `Child`가 `staticM()`, `instanceM()`을 각각 똑같은 시그니처로 가지고 있을 때 출력은? 이유도 함께 서술하세요.

<details><summary>답 보기</summary>

```
Parent.staticM
Child.instanceM
```

`static` 메서드는 **오버라이딩이 아니라 하이딩(hiding)** 이다. 클래스에 속하므로 다형성의 대상이 아니고, **선언 타입 기준으로 컴파일 시점에 결정**된다. 그래서 `p`가 실제로는 `Child`여도 `Parent.staticM()`이 호출된다.

덧붙여, `p.staticM()`처럼 **인스턴스 참조로 static 메서드를 호출하는 것 자체가 오해를 부르는 나쁜 습관**이다. `Parent.staticM()`처럼 클래스명으로 호출해야 의도가 드러난다(IDE도 경고를 띄운다).

</details>

#### C-4. 🟡
```java
Animal a = new Dog("바둑이");
Cat c = (Cat) a;
```
이 코드는 **컴파일은 통과하지만 실행 시 예외가 발생**합니다.
① 어떤 예외인지 ② 컴파일러는 왜 못 막는지 ③ 올바른 작성법 두 가지를 쓰세요.

<details><summary>답 보기</summary>

① `ClassCastException` (`class Dog cannot be cast to class Cat`)

② 컴파일러는 선언 타입만 본다. `a`의 선언 타입은 `Animal`이고 `Cat`은 `Animal`의 자식이므로, **"실행 시점에 a가 실제로 Cat일 가능성"** 이 문법적으로 존재한다. 컴파일러는 그 가능성을 부정할 수 없으므로 통과시키고, 실제 객체 확인은 런타임에 JVM이 한다.
(반대로 `String s = (String) a;`처럼 상속 관계가 아예 없으면 컴파일 에러가 난다.)

③ 올바른 작성법
```java
// instanceof로 확인 후 캐스팅
if (a instanceof Cat) {
    Cat c = (Cat) a;
    c.scratch();
}

// Java 16+ 패턴 매칭 (확인 + 캐스팅 + 변수 선언을 한 번에)
if (a instanceof Cat c) {
    c.scratch();
}
```
근본적으로는 **다운캐스팅과 `instanceof` 분기가 자주 등장한다는 것 자체가 설계 신호**다. 그 동작을 부모 타입의 메서드로 올려 다형성으로 처리할 수 없는지 먼저 검토해야 한다.

</details>

#### C-5. 🟢
오버라이딩과 오버로딩을 **① 목적 ② 위치 ③ 시그니처 ④ 바인딩 시점** 네 가지 기준으로 비교해 서술하세요.

<details><summary>답 보기</summary>

| 기준 | 오버라이딩 | 오버로딩 |
|------|-----------|---------|
| 목적 | 부모가 정의한 동작을 자식이 **자기 방식으로 재정의** | 같은 의미의 작업을 **여러 입력 형태로** 제공 |
| 위치 | 상속 관계(부모 ↔ 자식) | 같은 클래스 안 (상속과 무관) |
| 시그니처 | 이름·매개변수 **완전히 동일** (반환형은 공변 허용) | 이름만 같고 매개변수 **반드시 다름** (반환형만 다른 건 불가) |
| 바인딩 | **런타임**, 실제 객체 기준 (동적) | **컴파일 타임**, 선언 타입 기준 (정적) |

한 문장 구분법: **오버라이딩은 "같은 요청, 다른 응답"(다형성의 핵심)이고, 오버로딩은 "다른 요청, 같은 이름"(편의 문법)이다.** 오버로딩은 사실 다형성과 직접 관련이 없다.

</details>

### D. 추상클래스 vs 인터페이스

#### D-1. 🟢
추상클래스로는 할 수 있지만 인터페이스로는 할 수 없는 것 **2가지**, 반대로 인터페이스만 할 수 있는 것 **1가지**를 쓰고 각각의 이유를 설명하세요.

<details><summary>답 보기</summary>

**추상클래스만 가능**
1. **인스턴스 필드(상태) 보유** — `protected String name;` 처럼 자식들이 공유할 상태를 물려줄 수 있다. 인터페이스의 변수는 전부 `public static final` 상수다.
2. **생성자 보유** — 자식이 `super(...)`로 호출해 공통 필드를 초기화한다. 인터페이스는 인스턴스화 대상이 아니므로 생성자가 없다.
   (추가: `protected`/`private` 같은 다양한 접근 제어자 사용)

**인터페이스만 가능**
- **다중 구현** — `class Duck extends Animal implements Swimmable, Flyable`처럼 여러 계약을 동시에 지킬 수 있다. 클래스 상속은 단 하나뿐이라 자바에서 다중 상속의 이점을 얻는 유일한 통로다.

</details>

#### D-2. 🟡
`Duck`, `Fish`는 `Animal`을 상속하고, `Submarine`은 `Animal`과 아무 상속 관계가 없습니다.
그런데도 셋을 `List<Swimmable>` 하나에 담을 수 있습니다.
이 사례가 보여주는 **인터페이스의 본질적 가치**를 서술하세요.

<details><summary>답 보기</summary>

상속 계층은 **"무엇인가(is-a)"라는 하나의 축**으로만 세상을 분류한다. 그 축에서 잠수함과 오리는 영원히 만날 수 없다(잠수함은 동물이 아니다).

인터페이스는 이 계층과 **직교하는 별개의 축, 즉 "무엇을 할 수 있는가(can-do)"로 타입을 묶는다.** 덕분에 출신 계층이 전혀 다른 것들도 **행동 규약만 같으면 동일하게 취급**할 수 있다.

실무적 가치:
- **결합도 감소**: 함수가 `Duck`이 아니라 `Swimmable`에 의존하면, 나중에 어떤 클래스가 오든 계약만 지키면 동작한다(DIP).
- **테스트 용이성**: 실제 구현 대신 테스트용 가짜 구현체를 끼워 넣을 수 있다.
- 표준 라이브러리의 `Comparable`, `Iterable`, `Runnable`이 정확히 이 원리다. 서로 아무 관계 없는 클래스들이 `Comparable`만 구현하면 전부 `Collections.sort()`로 정렬된다.

</details>

#### D-3. 🟡
자바 8에서 인터페이스에 `default` 메서드가 추가되었습니다.
**왜 필요했는지**(도입 배경)와, 그로 인해 생긴 **부작용 및 해결책**을 서술하세요.

<details><summary>답 보기</summary>

**도입 배경**: 인터페이스에 메서드를 하나 추가하면 **기존의 모든 구현 클래스가 컴파일 에러**가 난다. 자바 8에서 `Collection`에 `stream()`, `forEach()`를 넣으려 했는데, 그러면 전 세계의 모든 `Collection` 구현체가 깨진다. `default` 메서드는 **기존 구현체를 건드리지 않고 인터페이스를 확장(하위 호환)** 하기 위해 도입되었다.

**부작용**: 두 인터페이스가 같은 시그니처의 `default` 메서드를 가지면 어느 쪽을 상속할지 모호해진다(다이아몬드 문제의 축소판).
> `class Duck inherits unrelated defaults for move() from types Swimmable and Flyable`

**해결책**: 자바는 자동으로 고르지 않고 **구현 클래스가 명시적으로 재정의하도록 강제**한다.
```java
@Override
public void move() {
    Swimmable.super.move();   // 원하는 쪽을 골라 호출
}
```
확인: `javac 01-객체지향이란/examples/errors/Err02_DefaultConflict.java` → `java 01-객체지향이란/examples/Ex04_AbstractVsInterface.java`

</details>

#### D-4. 🟡
추상클래스는 `new`로 인스턴스를 만들 수 없습니다. **그런데 왜 생성자를 가지고 있을까요?**

<details><summary>답 보기</summary>

**자식 객체를 만들 때 부모 부분을 초기화해야 하기 때문**이다.

`new Cat("나비")`를 하면 메모리에는 Cat 객체 하나가 만들어지지만, 그 안에는 Animal에서 물려받은 `name` 필드가 함께 들어 있다. 이 부분을 초기화하는 코드가 바로 추상클래스의 생성자이고, 자식이 `super(name)`으로 호출한다.

즉 추상클래스의 생성자는 **"단독으로 객체를 만들기 위한 것"이 아니라 "자식 객체의 일부를 초기화하기 위한 것"** 이다. 그래서 추상클래스의 생성자는 `public`일 필요가 없고 `protected`가 더 적절한 경우가 많다.

같은 이유로 인터페이스에는 생성자가 없다 — 초기화할 인스턴스 상태 자체가 없기 때문이다.

</details>

#### D-5. 🔴 설계 문제
쇼핑몰에 **카드 / 계좌이체 / 포인트** 세 가지 결제 수단이 있습니다. 요구사항은 다음과 같습니다.

- 모든 결제 수단은 `pay(금액)`을 할 수 있어야 한다.
- 모든 결제 수단은 결제 시각과 주문번호를 기록하고, 로그를 남기는 절차가 **완전히 동일**하다.
- 카드와 계좌이체는 **환불**이 가능하지만 포인트는 불가능하다.
- 나중에 "결제 수단은 아니지만 환불 처리는 해야 하는" 쿠폰 시스템이 추가될 수 있다.

추상클래스와 인터페이스를 각각 어디에 쓸지 정하고 **그 근거**를 서술하세요.

<details><summary>답 보기</summary>

**설계**
```java
// 공통 상태(주문번호·결제시각)와 동일한 로그 절차를 물려주므로 → 추상클래스
abstract class Payment {
    protected String orderId;
    protected LocalDateTime paidAt;

    public final void pay(int amount) {   // 공통 절차는 부모가 확정
        validate(amount);
        doPay(amount);                    // 수단별로 다른 부분만 자식에게 위임
        this.paidAt = LocalDateTime.now();
        log();
    }
    protected abstract void doPay(int amount);
    private void log() { /* 모든 수단이 동일 → 한 번만 작성 */ }
}

// 일부만 가지는 선택적 능력이고, 결제 수단이 아닌 것(쿠폰)도 가질 수 있으므로 → 인터페이스
interface Refundable {
    void refund(int amount);
}

class CardPayment     extends Payment implements Refundable { }
class TransferPayment extends Payment implements Refundable { }
class PointPayment    extends Payment { }              // 환불 불가
class Coupon          implements Refundable { }        // Payment가 아니지만 환불은 가능
```

**근거**
- `Payment`를 **추상클래스**로: ① `orderId`, `paidAt`이라는 **공통 상태**를 물려줘야 하고 ② 로그 절차가 **완전히 동일한 구현**이라 한 곳에만 쓰는 게 맞으며 ③ 세 가지 모두 "결제 수단**이다**"(is-a)를 만족한다.
- `Refundable`을 **인터페이스**로: ① **일부만 가지는 선택적 능력**이라 부모에 두면 포인트가 지원하지 않는 `refund()`를 물려받게 되어 리스코프 치환 원칙이 깨진다 ② 쿠폰처럼 **계층이 다른 클래스**도 이 능력을 가질 수 있어야 한다("환불할 수 있다", can-do).
- 부수 효과: `List<Refundable>`로 결제와 쿠폰을 함께 일괄 환불 처리할 수 있고, `pay()`를 `final`로 막아 절차 누락(템플릿 메서드 패턴)을 방지한다.

**판단 기준 정리**: 물려줄 **상태·공통 구현**이 있고 **모두가** 해당하면 추상클래스, **일부만** 가지거나 **계층을 넘나드는 능력**이면 인터페이스.

</details>

### E. 종합

#### E-1. 🟡
아래 코드를 다형성을 이용해 리팩터링하고, **무엇이 개선되는지** 설명하세요.
```java
public int calculateFee(String type, int amount) {
    if (type.equals("CARD"))        return amount + 100;
    else if (type.equals("BANK"))   return amount + 500;
    else if (type.equals("POINT"))  return amount;
    else throw new IllegalArgumentException("알 수 없는 타입");
}
```

<details><summary>답 보기</summary>

```java
interface PaymentMethod {
    int calculateFee(int amount);
}
class Card  implements PaymentMethod { public int calculateFee(int a) { return a + 100; } }
class Bank  implements PaymentMethod { public int calculateFee(int a) { return a + 500; } }
class Point implements PaymentMethod { public int calculateFee(int a) { return a; } }

// 호출부
int fee = method.calculateFee(amount);
```

**개선점**
1. **확장 시 기존 코드 수정 불필요**: 새 결제 수단은 클래스 추가만으로 끝난다(OCP).
2. **분기 누락 방지**: 원래 코드에서는 수수료 계산·한도 검사·취소 로직마다 똑같은 `if-else`가 흩어지고, 새 타입 추가 시 하나라도 빠뜨리면 런타임에 조용히 틀린다. 다형성으로 바꾸면 **인터페이스를 구현하지 않으면 컴파일이 안 되므로** 누락이 컴파일 타임에 잡힌다.
3. **문자열 타입 제거**: `"CARD"` 오타는 컴파일러가 못 잡지만 타입은 잡는다.
4. **응집도 향상**: 카드에 관한 규칙이 `Card` 클래스 한 곳에 모인다.

(선택지가 고정적이고 로직이 단순하다면 `enum`에 추상 메서드를 두는 방식도 좋은 대안이다.)

</details>

#### E-2. 🔴
후배 개발자가 묻습니다. **"다형성이 좋다는 건 알겠는데, 결국 `if-else`를 클래스로 흩어놓는 것 아닌가요? 오히려 코드를 따라가기 어려워지는데요."**
이 질문에 답하되, **후배 말이 맞는 경우**도 함께 인정하며 판단 기준을 제시하세요.

<details><summary>답 보기</summary>

**후배 말이 맞는 부분**: 다형성은 분기를 없애는 게 아니라 **분기 시점을 "객체를 생성하는 순간"으로 옮기는 것**이다. 코드를 읽을 때 실제로 어느 구현이 실행되는지 한눈에 안 보이고(간접성 비용), 클래스 파일 수가 늘어난다. 로직이 세 줄짜리 `if-else` 하나뿐이고 타입이 늘어날 계획이 없다면 **다형성은 과잉 설계**다.

**그럼에도 다형성이 이기는 조건**
1. **같은 분기가 여러 곳에 반복될 때** — `if-else`는 N개 지점에 흩어지지만 다형성은 클래스 하나에 모인다. 새 타입 추가 시 컴파일러가 누락을 잡아준다.
2. **타입이 계속 늘어날 때** — 확장이 "추가"로 끝나는가, "기존 코드 수정"을 요구하는가의 차이다.
3. **각 분기의 로직이 커질 때** — 분기마다 수십 줄이면 하나의 거대 메서드보다 클래스 분리가 압도적으로 읽기 쉽다.

**판단 기준 한 문장**: **"분기가 한 곳뿐이고 늘어나지 않을 것 같으면 `if-else`, 같은 분기가 반복되거나 종류가 늘어날 것 같으면 다형성."**
설계는 미래의 변경 비용을 사는 일이고, 변하지 않을 것에 지불하는 값은 낭비다.

</details>

- [ ] 부모에 기본 생성자가 없을 때 나는 에러와 해결책 3가지를 안다
- [ ] "부를 수 있는가는 선언 타입, 어떻게 동작하는가는 실제 객체" 원칙으로 오버로딩/오버라이딩/필드 하이딩을 모두 설명할 수 있다
- [ ] 다운캐스팅이 컴파일은 되는데 런타임에 터지는 이유를 안다
- [ ] 추상클래스와 인터페이스 중 무엇을 쓸지 근거를 대며 정할 수 있다
- [ ] `default` 메서드가 왜 생겼고 충돌 시 어떻게 해결하는지 안다
